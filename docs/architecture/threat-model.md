# Моделювання загроз (STRIDE)

Документ містить архітектурний аналіз безпеки за методологією STRIDE. Аналіз проведено для кожного компонента системи та кожної межі довіри (Trust Boundary) з [діаграми розгортання](./uml/deployment-diagram.puml) фінальної версії (v1.2.0): застосунок на Render, база даних Neon PostgreSQL, TMDB API, поштовий ретранслятор Google Apps Script і конвеєр GitHub Actions.

## 1. Об'єкти аналізу

**Межі довіри (Trust Boundaries - TB):**
* **TB-01 (Internet):** Web Browser ↔ Web Server (Render). Перехід від пристрою користувача до нашого сервера (публічна мережа, HTTPS).
* **TB-02 (Data):** Web Server (Render) ↔ Neon PostgreSQL. Сервер і база даних належать різним провайдерам, тож з'єднання проходить через Інтернет і захищене TLS (`sslmode=require`) та обліковими даними з `DATABASE_URL`.
* **TB-03 (External API):** Web Server ↔ TMDB API. Перехід від нашої системи до стороннього провайдера.
* **TB-04 (Mail relay):** Web Server ↔ Google Apps Script ↔ Gmail. Листи підтвердження email і відновлення пароля.
* **TB-05 (CI/CD):** GitHub Actions / GitHub Container Registry ↔ Production. Перевірка коду, розгортання, keep-alive і публікація образу.

**Компоненти (Components - C):**
* **C-01:** React Application (Frontend)
* **C-02:** FastAPI Application (Backend)
* **C-03:** PostgreSQL Instance (Database)
* **C-04:** Mail relay (Google Apps Script `mailer.gs` + Gmail)
* **C-05:** TMDB API (External Service)

Окремого кеш-сервера (Redis) немає: обмеження частоти запитів зберігаються в пам'яті процесу FastAPI (див. [HLD, розділ 2.3](./high-level-design.md)).

## 2. Межі довіри (Trust Boundaries)

### TB-01: Web Browser ↔ Web Server (Public Internet)
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Зловмисник перехоплює сесійний токен у відкритій Wi-Fi мережі та виконує запити від імені легітимного користувача. | Висока | HTTPS на Render і заголовок HSTS (`security_headers.py`). Зберігання JWT у `HttpOnly`, `Secure`, `SameSite=Lax` cookies. |
| **T**ampering | Чи можна змінити дані в дорозі? | MitM-атака модифікує HTTP-пакети, змінюючи текст рецензії або оцінку перед тим, як вони потраплять на сервер. | Висока | Обов'язкове використання SSL/TLS (HTTPS) для шифрування каналу передачі даних. |
| **R**epudiation | Чи може учасник заперечити дію? | Користувач залишає образливий коментар, а після блокування стверджує, що хтось інший відправив цей запит. | Середня | Логування IP-адреси, `User-Agent` та часу доступу для всіх мутуючих запитів. |
| **I**nformation disclosure | Чи можуть дані витекти? | Трафік між клієнтом і сервером прослуховується, розкриваючи персональні вподобання, списки переглядів та email. | Висока | Передача даних виключно через зашифрований HTTPS-канал. |
| **D**enial of service | Чи можна вивести межу з ладу? | Ботнет генерує тисячі HTTP-запитів на секунду до відкритого ендпоінту авторизації. | Висока | Rate Limiting у FastAPI (`services/rate_limit.py`): 5 невдалих входів за хвилину з однієї адреси, обмеження реєстрацій, листів і коментарів; відповідь 429 з `Retry-After`. |
| **E**levation of privilege | Чи може отримати зайві права? | Маніпуляція HTTP-заголовками або спроба відправити змінений JWT з роллю `admin`. | Висока | Криптографічна валідація підпису токена на бекенді (ігнорування будь-яких непідписаних змін у payload). |

### TB-02: Web Server (Render) ↔ Neon PostgreSQL
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Зловмисник, що дізнався адресу бази Neon, підключається до неї від імені застосунку. | Висока | Доступ лише за роллю й паролем із `DATABASE_URL`; рядок підключення зберігається тільки в Environment на Render і не потрапляє в репозиторій (перевірка gitleaks у CI). |
| **T**ampering | Чи можна змінити дані в дорозі? | MitM між Render і Neon змінює SQL-запити, бо обидва сервіси спілкуються через Інтернет. | Висока | Neon приймає лише TLS-з'єднання (`sslmode=require`), сертифікат сервера перевіряється драйвером. |
| **R**epudiation | Чи може учасник заперечити дію? | Сервер надсилає команду на видалення даних у БД, але через збій мережі невідомо, чи транзакція пройшла. | Низька | ACID-транзакції PostgreSQL; при помилці сесія SQLAlchemy відкочується, а клієнт отримує помилку замість часткового запису. |
| **I**nformation disclosure | Чи можуть дані витекти? | Перехоплення трафіку розкриває email і хеші паролів. | Середня | TLS на всьому шляху; паролі зберігаються лише як bcrypt-хеші, токени скидання пароля — лише як SHA-256. |
| **D**enial of service | Чи можна вивести межу з ладу? | Забагато одночасних з'єднань вичерпує пул, або «приспана» база Neon довго прокидається й запити зависають. | Висока | Пулінг через PgBouncer (pooled endpoint Neon) і пул SQLAlchemy з `pool_pre_ping`, тайм-аутами підключення, очікування пулу й `statement_timeout`; keep-alive кожні 10 хвилин. |
| **E**levation of privilege | Чи може отримати зайві права? | Застосунок підключається до БД роллю-власником, тож вразливість дозволила б `DROP TABLE`. | Середня | Ризик частково приймається (безкоштовний план Neon, одна роль); SQL лише через ORM з параметрами; дані можна відновити з історії змін Neon у межах вікна безкоштовного плану. |

### TB-03: Web Server ↔ TMDB API (External API)
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Атака DNS Spoofing перенаправляє запити від нашого сервера на підроблений сервер TMDB. | Низька | Перевірка справжності TLS-сертифіката стороннього API стандартними бібліотеками. |
| **T**ampering | Чи можна змінити дані в дорозі? | Зловмисник підміняє відповіді від TMDB, впроваджуючи шкідливий JavaScript у поля з описом фільму. | Середня | Сувора санітизація та екранування всіх даних, що надходять від TMDB, на бекенді. |
| **R**epudiation | Чи може учасник заперечити дію? | Сторонній сервіс заперечує, що відправив некоректні дані, які викликали збій нашого бекенду. | Низька | Ризик приймається (ми не контролюємо логування TMDB). Логуємо всі нестандартні відповіді у себе. |
| **I**nformation disclosure | Чи можуть дані витекти? | Наш секретний TMDB API Key передається у відкритому вигляді через URL і зберігається у логах провайдера. | Середня | Передавати API-ключ через HTTP-заголовки (якщо підтримується TMDB) та виключно через HTTPS. |
| **D**enial of service | Чи можна вивести межу з ладу? | TMDB обмежує доступ (Rate Limit), або сервіс тимчасово недоступний, що блокує роботу нашої системи. | Висока | Метадані TMDB імпортуються один раз і зберігаються в PostgreSQL; патерн Fallback (показ збережених даних або локального резервного набору). |
| **E**levation of privilege | Чи може отримати зайві права? | Зловмисник викрадає наш TMDB API Key і використовує його для вичерпання нашої платної квоти. | Висока | Зберігання ключа у `.env` (без коміту в Git). Регулярна ротація ключів. |

### TB-04: Web Server ↔ Google Apps Script ↔ Gmail (Mail relay)
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Сторонній знаходить URL вебзастосунку Apps Script і розсилає від нашого імені фішингові листи. | Висока | Скрипт приймає лише запити зі спільним секретом (`GOOGLE_SCRIPT_SECRET` ↔ `MAILER_SECRET`) і лише одного звичайного адресата на лист. |
| **T**ampering | Чи можна змінити дані в дорозі? | Підміна URL ретранслятора у налаштуваннях спрямовує листи з токенами на чужий сервер. | Середня | Бекенд приймає лише `https://script.google.com/macros/...` (перевірка в `services/email.py`); HTTPS із перевіркою сертифіката. |
| **R**epudiation | Чи може учасник заперечити дію? | Користувач стверджує, що не запитував скидання пароля. | Низька | Час останнього листа зберігається (`password_reset_sent_at`, `verification_sent_at`); листи надсилаються лише на адресу акаунта. |
| **I**nformation disclosure | Чи можуть дані витекти? | Токен із листа перехоплюють або він лишається в базі й після використання. | Висока | У базі лише SHA-256 токена; посилання діє 1 годину й одноразове; відповідь на «Забули пароль?» однакова для наявних і відсутніх email (без перебору адрес). |
| **D**enial of service | Чи можна вивести межу з ладу? | Масові запити реєстрації й скидання пароля вичерпують денну квоту Gmail («поштова бомба»). | Висока | Ліміти листів на адресу й годину (429), повторний лист не частіше ніж раз на інтервал, тайм-аут 10 с, відправлення у фоні (BackgroundTasks). |
| **E**levation of privilege | Чи може отримати зайві права? | Зловмисник із посиланням скидання пароля захоплює акаунт і зберігає старі сесії жертви. | Висока | Після зміни пароля `token_version` збільшується, тож усі раніше видані JWT стають недійсними; новий пароль — щонайменше 8 символів. |

### TB-05: GitHub Actions / GHCR ↔ Production
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Зловмисний PR видає свій код за перевірений і потрапляє у production. | Висока | `main` захищена: злиття лише через PR із пройденою перевіркою `build` і рев'ю; Render розгортає тільки коміти з `main`. |
| **T**ampering | Чи можна змінити дані в дорозі? | Скомпрометована залежність потрапляє в образ. | Висока | `requirements-lock.txt` із sha256 (`pip install --require-hashes`), `npm ci --ignore-scripts`, оновлення від Dependabot, bandit у CI. |
| **R**epudiation | Чи може учасник заперечити дію? | Невідомо, яка версія і коли потрапила в production. | Низька | Workflow «Production deployment» записує кожне розгортання в GitHub Deployments із SHA коміту. |
| **I**nformation disclosure | Чи можуть дані витекти? | Секрет потрапляє в репозиторій або лог Actions. | Висока | gitleaks у CI; секрети production лише на Render; GitHub маскує секрети в логах; keep-alive працює з `permissions: {}`. |
| **D**enial of service | Чи можна вивести межу з ладу? | Поламана збірка блокує розгортання. | Середня | Render не перемикає трафік, доки `/health/live` нової версії не відповідає; попередня версія лишається активною. |
| **E**levation of privilege | Чи може отримати зайві права? | Workflow з широкими правами `GITHUB_TOKEN` змінює репозиторій. | Середня | Мінімальні `permissions` у кожному workflow (`contents: read` для публікації образу, запис лише там, де він потрібен). |

## 3. Компоненти (Components)

### C-01: React Application (Frontend)
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | XSS-вразливість у React краде дані з `localStorage`, дозволяючи клонувати сесію. | Висока | Не зберігати токени в `localStorage`. Використовувати `HttpOnly` cookies. |
| **T**ampering | Чи можна змінити дані у сховищі? | Користувач модифікує стан Redux через консоль браузера, щоб зробити активною кнопку "Видалити чужий відгук". | Низька | Frontend лише відображає дані. Усі перевірки прав доступу виконуються на бекенді. |
| **R**epudiation | Чи може учасник заперечити дію? | Користувач випадково видаляє список "До перегляду" і стверджує, що це помилка UI. | Низька | Додавання модального вікна підтвердження ("Ви впевнені?") для критичних дій. |
| **I**nformation disclosure | Чи можуть дані витекти? | Чутливі дані кешуються браузером і доступні іншим користувачам на спільному комп'ютері. | Середня | Відключення кешування для сторінок профілю (`Cache-Control: no-store`). |
| **D**enial of service | Чи можна вивести компонент з ладу? | Сторінка намагається відрендерити 10 000 відгуків одночасно, що призводить до зависання вкладки браузера. | Середня | Впровадження пагінації (Pagination) або віртуалізації списків. |
| **E**levation of privilege | Чи може отримати зайві права? | Зловмисник змінює булевий прапорець `isAdmin=true` у локальному стані React. | Низька | Навіть якщо UI покаже панель адміністратора, API відхилить запит через відсутність прав у токені (403). |

### C-02: FastAPI Application (Backend)
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Алгоритм підпису JWT використовує слабкий секретний ключ, який зламали методом brute-force. | Висока | Використання надійного `SECRET_KEY` (від 32 байт) та алгоритму HS256/RS256. |
| **T**ampering | Чи можна змінити дані у сховищі? | Вразливість типу Insecure Deserialization дозволяє змінити логіку роботи бекенду. | Середня | Валідація всіх вхідних даних виключно через строгі схеми Pydantic. |
| **R**epudiation | Чи може учасник заперечити дію? | Відсутність логування дій адміністратора у FastAPI не дозволяє провести аудит інцидентів. | Середня | Інтеграція логера, що фіксує кожну мутацію даних у БД з прив'язкою до `user_id`. |
| **I**nformation disclosure | Чи можуть дані витекти? | У разі збою системи (HTTP 500) FastAPI повертає клієнту Stack Trace з рядками вихідного коду. | Середня | Глобальний Exception Handler, що приховує деталі помилки від кінцевого користувача. |
| **D**enial of service | Чи можна вивести компонент з ладу? | Важкий ендпоінт пошуку викликається синхронно, блокуючи робочі потоки Uvicorn. | Середня | Виконання важких обчислень в асинхронному режимі. |
| **E**levation of privilege | Чи може отримати зайві права? | BOLA-вразливість: користувач передає `ID` чужої рецензії і видаляє її. | Висока | Обов'язкова перевірка `if review.user_id != current_user.id: raise HTTPException(403)`. |

### C-03: PostgreSQL Instance (Database)
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Атакуючий отримує доступ до консолі сервера БД і підключається без пароля (trust auth). | Висока | Керована база Neon: прямого доступу до хоста немає, автентифікація ролі паролем (SCRAM) через TLS; консоль Neon — лише для учасників команди. |
| **T**ampering | Чи можна змінити дані у сховищі? | Використання конкатенації рядків у SQL замість параметрів призводить до SQL-ін'єкції. | Висока | Використання ORM (SQLAlchemy) та параметризованих запитів. Заборона "сирих" SQL рядків. |
| **R**epudiation | Чи може учасник заперечити дію? | Хтось напряму видалив записи з бази через `psql`, і неможливо встановити винуватця. | Низька | Обмеження прямого доступу. Для production: увімкнення `pgAudit`. |
| **I**nformation disclosure | Чи можуть дані витекти? | Втрата фізичного диска сервера або бекапу розкриває всі користувацькі дані. | Середня | Паролі зберігаються як bcrypt-хеші. Neon шифрує дані на диску. |
| **D**enial of service | Чи можна вивести компонент з ладу? | Відсутність індексів призводить до Full Table Scan, що "кладе" БД під навантаженням. | Висока | Створення B-Tree індексів на стовпцях `title` та `user_id`. |
| **E**levation of privilege | Чи може отримати зайві права? | Вразливість у БД дозволяє виконати системну команду на хості сервера. | Середня | Хост бази керує Neon; застосунок не виконує довільних SQL-команд від користувача. |

### C-04: Mail relay (Google Apps Script + Gmail)

## 4. Відображення контрзаходів в архітектурному дизайні (Feedback Loop)

Усі визначені контрзаходи STRIDE безпосередньо інтегровані в проєктний дизайн системи:
1. **Автентифікація та захист токенів (TB-01, C-01):** Зберігання та передача токенів реалізована виключно через `HttpOnly`, `Secure`, `SameSite=Lax` cookies, що блокує крадіжку сесії через XSS. Це рішення зафіксоване в [High-Level Design](./high-level-design.md), на [діаграмі послідовності](./uml/sequence-diagram.puml) та в рядку `SEC-001` [матриці простежуваності](./traceability-matrix.md).
2. **Захист від ін'єкцій та санітизація (TB-01, TB-03, C-02):** Сувора валідація схем через Pydantic та параметризація SQL-запитів через SQLAlchemy ORM.
3. **Захист з'єднання з базою (TB-02):** Render і Neon спілкуються лише через TLS (`sslmode=require`), облікові дані — тільки в Environment на Render; пул з'єднань і тайм-аути захищають від вичерпання з'єднань.
4. **Стійкість до відмов (TB-03, C-05):** Fallback на збережені в БД метадані або локальний резервний набір при збоях TMDB API для виконання вимоги доступності REL-001.
5. **Листи й відновлення пароля (TB-04, C-04):** Спільний секрет ретранслятора, ліміти листів, одноразові токени з терміном дії, збереження лише їх SHA-256 і `token_version`, що завершує всі сесії після зміни пароля.
6. **Ланцюг постачання (TB-05):** Захищена гілка `main`, заблоковані версії залежностей із хешами, gitleaks, bandit, Dependabot і мінімальні права workflow.
