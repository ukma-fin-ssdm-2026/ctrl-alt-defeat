# Моделювання загроз (STRIDE)

Документ містить архітектурний аналіз безпеки за методологією STRIDE. Аналіз проведено для кожного компонента системи та кожної межі довіри (Trust Boundary), виявленої на діаграмі розгортання проєкту.

## 1. Об'єкти аналізу

**Межі довіри (Trust Boundaries - TB):**
* **TB-01 (Internet):** Web Browser ↔ Web Server. Перехід від пристрою користувача до нашого сервера (публічна мережа).
* **TB-02 (Internal VPC):** Web Server ↔ PostgreSQL / Redis. Перехід між бекендом та сховищами даних (внутрішня мережа).
* **TB-03 (External API):** Web Server ↔ TMDB API. Перехід від нашої системи до стороннього провайдера.

**Компоненти (Components - C):**
* **C-01:** React Application (Frontend)
* **C-02:** FastAPI Application (Backend)
* **C-03:** PostgreSQL Instance (Database)
* **C-04:** Redis Instance (Cache)
* **C-05:** TMDB API (External Service)

## 2. Межі довіри (Trust Boundaries)

### TB-01: Web Browser ↔ Web Server (Public Internet)
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Зловмисник перехоплює сесійний токен у відкритій Wi-Fi мережі та виконує запити від імені легітимного користувача. | Висока | Використання HSTS (тільки HTTPS). Зберігання JWT у `HttpOnly` та `Secure` cookies. |
| **T**ampering | Чи можна змінити дані в дорозі? | MitM-атака модифікує HTTP-пакети, змінюючи текст рецензії або оцінку перед тим, як вони потраплять на сервер. | Висока | Обов'язкове використання SSL/TLS (HTTPS) для шифрування каналу передачі даних. |
| **R**epudiation | Чи може учасник заперечити дію? | Користувач залишає образливий коментар, а після блокування стверджує, що хтось інший відправив цей запит. | Середня | Логування IP-адреси, `User-Agent` та часу доступу для всіх мутуючих запитів. |
| **I**nformation disclosure | Чи можуть дані витекти? | Трафік між клієнтом і сервером прослуховується, розкриваючи персональні вподобання, списки переглядів та email. | Висока | Передача даних виключно через зашифрований HTTPS-канал. |
| **D**enial of service | Чи можна вивести межу з ладу? | Ботнет генерує тисячі HTTP-запитів на секунду до відкритого ендпоінту авторизації. | Висока | Налаштування Rate Limiting на рівні API Gateway / FastAPI (обмеження запитів з однієї IP). |
| **E**levation of privilege | Чи може отримати зайві права? | Маніпуляція HTTP-заголовками або спроба відправити змінений JWT з роллю `admin`. | Висока | Криптографічна валідація підпису токена на бекенді (ігнорування будь-яких непідписаних змін у payload). |

### TB-02: Web Server ↔ PostgreSQL / Redis (Internal VPC)
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Інший скомпрометований контейнер у цій же мережі видає себе за FastAPI і підключається до БД. | Середня | Налаштування `pg_hba.conf` (доступ лише для IP FastAPI) та автентифікація за паролем. |
| **T**ampering | Чи можна змінити дані в дорозі? | Трафік усередині VPC не шифрується. Зловмисник, що проник у мережу, змінює SQL-запити "на льоту". | Середня | На етапі MVP ризик приймається. В production: налаштування `sslmode=require` для БД. |
| **R**epudiation | Чи може учасник заперечити дію? | Сервер надсилає команду на видалення даних у БД, але через збій мережі невідомо, чи транзакція пройшла. | Низька | Використання механізму ACID транзакцій у PostgreSQL та логування на рівні ORM. |
| **I**nformation disclosure | Чи можуть дані витекти? | Перехоплення нешифрованого TCP-трафіку всередині VPC розкриває паролі користувачів (навіть хешовані) під час їх перевірки. | Середня | Ізоляція VPC на рівні хмарного провайдера, заборона зовнішнього доступу до портів 5432 та 6379. |
| **D**enial of service | Чи можна вивести межу з ладу? | FastAPI відкриває забагато одночасних з'єднань із БД, що призводить до Connection Pool Exhaustion. | Висока | Використання пулінгу з'єднань (наприклад, PgBouncer або налаштування пулу в SQLAlchemy). |
| **E**levation of privilege | Чи може отримати зайві права? | Сервер застосунків підключається до БД використовуючи підключення без обмежень ролей. | Середня | Створення окремого користувача БД із правами лише на потрібні таблиці (без `DROP` / `ALTER`). |

### TB-03: Web Server ↔ TMDB API (External API)
| Категорія | Питання STRIDE | Опис загрози (Сценарій) | Оцінка | Контрзахід / Рішення |
| :--- | :--- | :--- | :--- | :--- |
| **S**poofing | Чи може хтось видати себе за іншого? | Атака DNS Spoofing перенаправляє запити від нашого сервера на підроблений сервер TMDB. | Низька | Перевірка справжності TLS-сертифіката стороннього API стандартними бібліотеками. |
| **T**ampering | Чи можна змінити дані в дорозі? | Зловмисник підміняє відповіді від TMDB, впроваджуючи шкідливий JavaScript у поля з описом фільму. | Середня | Сувора санітизація та екранування всіх даних, що надходять від TMDB, на бекенді. |
| **R**epudiation | Чи може учасник заперечити дію? | Сторонній сервіс заперечує, що відправив некоректні дані, які викликали збій нашого бекенду. | Низька | Ризик приймається (ми не контролюємо логування TMDB). Логуємо всі нестандартні відповіді у себе. |

| **D**enial of service | Чи можна вивести межу з ладу? | TMDB обмежує доступ (Rate Limit), або сервіс тимчасово недоступний, що блокує роботу нашої системи. | Висока | Кешування відповідей TMDB у Redis; імплементація патерну Fallback (показ збережених даних). |
| **E**levation of privilege | Чи може отримати зайві права? | Зловмисник викрадає наш TMDB API Key і використовує його для вичерпання нашої платної квоти. | Висока | Зберігання ключа у `.env` (без коміту в Git). Регулярна ротація ключів. |
