# ADR-002: Вибір основної системи управління базами даних (СУБД)

**Статус:** Прийнято  
**Дата:** 2026-10-01  

## Контекст
* Система повинна зберігати користувачів, списки "До перегляду" (Watchlists), історію переглядів (Watched Lists), відгуки та числові рейтинги контенту.
* Дані мають чітку структуру та сильні зв'язки (реляційна природа: користувач -> фільм -> оцінка).
* Згідно з вимогами до надійності (REL-001), необхідне гарантоване збереження даних під час транзакцій (наприклад, при записі оцінки та перерахунку рейтингу), щоб уникнути пошкодження даних при збоях.

## Рішення
Використовувати **PostgreSQL** як основну реляційну базу даних для production-середовища (SQLite може використовуватися лише для локальної розробки).

## Наслідки
* **Плюси:** 
  * Повна підтримка ACID транзакцій забезпечує надійність при паралельному записі оцінок та рецензій.
  * Можливість створювати складні B-Tree індекси для швидкого сортування за рейтингом (`rating`) та датою випуску (`release_date`).
  * Підтримка повнотекстового або `ILIKE` пошуку з індексуванням для реалізації вимог щодо пошуку контенту.
* **Застереження:** 
  * Необхідно налаштувати регулярні бекапи та моніторинг пулу з'єднань, оскільки кожне підключення в PostgreSQL споживає пам'ять.
* **Мінуси:** 
  * Вертикальне і горизонтальне масштабування реляційної бази даних складніше порівняно з NoSQL рішеннями. Схема даних (схеми міграцій) вимагає суворого управління.

## Розглянуті альтернативи
* **MongoDB (NoSQL):** Відхилено. Хоча NoSQL забезпечує гнучкість схеми, наші дані високореляційні. Зв'язки між користувачами, фільмами та рецензіями через крос-таблиці (наприклад, `watchlist`, `watch_history`) простіше та безпечніше реалізувати в SQL.
* **SQLite для production:** Відхилено. SQLite підходить для розробки, але не витримає конкурентного доступу (100 одночасних користувачів) та вимог до швидкодії (PERF-001).
