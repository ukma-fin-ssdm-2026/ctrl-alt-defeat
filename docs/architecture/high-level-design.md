# Архітектурний огляд (High-Level Design)

Цей документ є головною точкою входу в архітектуру системи веб-платформи для кіноманів та любителів серіалів, що дозволяє відкривати новий контент, вести списки переглянутого (Watched List) та бажаного (Watchlist), виставляти числові оцінки (Rating), публікувати розгорнуті рецензії (Review) та отримувати персоналізовані рекомендації.

---

## 1. Архітектурний стиль

У проєкті застосовується **Багатошарова трирівнева архітектура (Three-Tier Architecture)**, обґрунтована в [ADR-001](./decisions/ADR-001.md):
* **Рівень представлення (Presentation Tier):** Односторінковий клієнтський веб-застосунок (SPA) на базі React 19, Tailwind CSS та Vite (керування станом, UI-компоненти, фільтрація, маршрутизація через React Router).
* **Рівень логіки та застосунку (Application/Logic Tier):** REST API бекенд на базі Python та асинхронного фреймворку FastAPI (маршрутизація, валідація схем через Pydantic, бізнес-правила, рекомендаційна система, автентифікація).
* **Рівень даних (Data Tier):** Реляційна база даних PostgreSQL 16 для надійного збереження транзакційних даних (локально за замовчуванням SQLite; СКБД обирається змінною `DATABASE_URL`). Окремий кеш-сервер (Redis) у поточній версії не використовується — див. розділ 2.3.

---

## 2. Декомпозиція компонентів та внутрішні модулі

Відповідно до [діаграми компонентів](./uml/component-diagram.puml), система розділена на чіткі функціональні модулі з визначеними зонами відповідальності:

### 2.1. Frontend (Presentation Tier)
* **UI Components & Views:** Презентаційні компоненти сторінок (каталог, деталі фільму, форма відгуку, профіль користувача).
* **Client State Management:** Збереження стану фільтрів, списків та контексту автентифікованого користувача.
* **API Client (Axios):** Ізольований HTTP-клієнт, що здійснює запити до бекенду з автоматичною передачею авторизаційних cookies (`credentials: 'include'`).

### 2.2. FastAPI Backend (Application Tier)
* **API Routers / Controllers (`src/api/routers`):** Обробники HTTP-запитів (`/api/v1/auth`, `/api/v1/movies`, `/api/v1/reviews`, `/api/v1/watchlist`, `/api/v1/users/me/watched`, `/api/v1/recommendations`, `/api/v1/comments`, `/api/v1/admin`), що здійснюють первинний парсинг вхідних даних та маршрутизацію.
* **Security & Auth Module:** Модуль безпеки, що виконує stateless-валідацію JWT-підпису токенів, витягнутих із `HttpOnly` cookie (або заголовка `Authorization`), та хешування паролів за допомогою алгоритму bcrypt.
* **Business Logic Layer (Services):**
  * *Rating & Review Services:* Реалізують правила FR-003 (дозволяє виставити числову оцінку 1–10 виключно для контенту зі списку переглянутого) та FR-004 (публікація розгорнутої рецензії 10–5000 символів).
  * *Content & Search Service:* Реалізує динамічну фільтрацію, пошук за назвою та жанрами (FR-002, FR-010) на рівні SQL-запитів до БД.
  * *Recommendation Engine:* Формування персоналізованих рекомендацій (FR-007) на основі оціненого та переглянутого контенту.
  * *TMDB Sync Client:* Клієнт імпорту метаданих з публічного TMDB API (FR-012): 100 популярних фільмів, 100 серіалів і 100 мультфільмів (`discover` + деталі з перекладами) з постерами (`image.tmdb.org`), описами, жанрами й тривалістю. Порожній каталог заповнюється автоматично під час старту застосунку (без ключа `TMDB_API_KEY` — з локального резервного набору), а адміністратор оновлює каталог кнопкою в адмін-панелі (фонове завдання). Фільми зіставляються за `tmdb_id` і ніколи не видаляються.
* **Data Access Layer / ORM (DAL):** Шар доступу до даних на базі SQLAlchemy 2.x, що абстрагує роботу з таблицями БД через репозиторії та керує пулом з'єднань із автоматичним перепідключенням (`pool_pre_ping=True`, `src/api/db/database.py`).
* **Static Frontend Serving (`src/api/frontend.py`):** У контейнерному розгортанні FastAPI віддає зібраний React-застосунок (`frontend/dist`) з того самого origin, що й API (вмикається змінною `FRONTEND_DIST_DIR`).

### 2.3. Data Tier
* **PostgreSQL:** Реляційна СУБД для постійного зберігання сутностей (`User`, `Content`, `Genre`, `Rating`, `Review`, `WatchlistItem`, `WatchedItem`, `Comment`, `Recommendation`, `Ban`, `ModerationReport`). Підтримує повну транзакційну цілісність (ACID).
* **Кешування (Redis) — не реалізовано, можливе розширення.** Поточний обсяг каталогу дозволяє виконувати вимогу PERF-001 (< 500 мс) прямими запитами до PostgreSQL з індексами, тому окремий кеш-сервер не розгортається. Redis розглядається як майбутнє розширення для кешування каталогу та Rate Limiting при зростанні навантаження. Сесії користувачів у будь-якому разі не зберігаються на сервері, оскільки автентифікація є stateless (JWT).

## 3. Опис інтерфейсів та єдиний стандарт автентифікації

Комунікація між компонентами системи відбувається за стандартизованими протоколами:

* **UI ↔ REST API Controllers:**
  * Протокол: HTTPS, формат даних: JSON.
  * **Єдиний стандарт автентифікації:** На основі аналізу загроз STRIDE (TB-01, C-01) для запобігання викраденню токенів через XSS автентифікація здійснюється через **stateless JWT-токени, що зберігаються та передаються у безпечних cookies з прапорцями `HttpOnly`, `Secure` та `SameSite=Lax`**. Крім того, підтримується заголовок `Authorization: Bearer <token>` для сторонніх API-інтеграцій та автоматизованого тестування.
* **Business Logic ↔ TMDB API:**
  * Протокол: HTTPS (зовнішній REST API). Запити виконуються асинхронно для імпорту постерів, синопсисів та жанрів. При тимчасовій недоступності застосовується патерн Fallback (віддача локально збережених даних).
* **Data Access Layer ↔ PostgreSQL:**
  * Протокол: TCP (порт 5432), передача SQL-запитів через драйвер `psycopg2` / SQLAlchemy ORM. Усі операції зміни даних виконуються в межах транзакцій із автоматичним `ROLLBACK` у разі помилки.

## 4. Архітектура розгортання (Deployment View)

Відповідно до [діаграми розгортання](./uml/deployment-diagram.puml), інфраструктура системи ізольована за трьома мережевими зонами та межами довіри (Trust Boundaries):

1. **Зона 1: Недовірена (Public Internet / TB-01):**
   * *Client Device (Desktop/Mobile):* Кінцевий користувач взаємодіє з додатком через сучасний веб-браузер. Статичні ресурси React-додатка завантажуються клієнтом, після чого виконуються захищені HTTPS-запити до REST API.
2. **Зона 2: Захищена приватна мережа (Internal VPC / TB-02):**
   * *Application Server (Docker Container):* Єдиний Docker-образ (`Dockerfile`, багатоетапна збірка): ASGI-сервер Uvicorn з бекендом FastAPI, який також віддає зібраний React-застосунок. Зовнішній трафік надходить по HTTPS (порт 443) через TLS-термінацію хостинг-платформи; всередині контейнера застосунок слухає порт `PORT` (8000 за замовчуванням). Онлайн-версія розгортається на Render як веб-сервіс із цього образу (регіон Frankfurt); сервісом керує Blueprint `render.yaml`, згенерований із наявного сервісу. Секрети зберігаються лише в налаштуваннях Render (`sync: false`), перевірка стану використовує `/health/live`, а Uvicorn довіряє заголовкам `X-Forwarded-*` проксі, щоб редиректи зберігали схему `https://`.
   * *Database Server (Managed PostgreSQL 16):* Керована serverless PostgreSQL (Neon, регіон Frankfurt), підключення лише через TLS (`sslmode=require`) за обліковими даними з `DATABASE_URL`, які зберігаються тільки в налаштуваннях хостингу. Обчислювальний вузол бази засинає без навантаження й прокидається при першому запиті. Локально (`docker-compose.yml`) PostgreSQL доступна лише у внутрішній мережі контейнерів.
   * *Локальний production-подібний запуск:* `docker-compose.yml` піднімає контейнер застосунку та PostgreSQL 16 з healthcheck і томом для даних.
3. **Зона 3: Зовнішні сервіси (Third-Party / TB-03):**
   * *TMDB API:* Зовнішній хмарний провайдер метаданих, взаємодія з яким відбувається виключно через захищений канал TLS (HTTPS).

## 5. Безперервна інтеграція та розгортання (CI/CD Pipeline)

Пайплайн безперервної інтеграції (MAINT-001) побудований на базі **GitHub Actions** і є невіддільною частиною архітектури системи:
* **Статичний аналіз та лінтинг:** При кожному Push та Pull Request автоматично запускаються перевірки форматування коду `black --check`, лінтер `ruff` (довжина рядка 120 символів, PEP 8) та лінтер фронтенду `eslint` (окремий job `frontend` разом із тестами Vitest і збиранням Vite).
* **Аналіз безпеки (SAST):** Сканування коду на наявність вразливостей інструментом `bandit` та перевірка всієї історії репозиторію на випадковий витік секретів за допомогою `gitleaks` (job `secrets`).
* **Автоматизоване тестування:** Прогін модульних та інтеграційних тестів за допомогою `pytest`, перевірка цільового покриття вихідного коду (Coverage ≥ 80%).
* **Автогенерація контрактів:** Автоматична перевірка та синхронізація специфікації OpenAPI (`openapi-generated.yaml`) безпосередньо з коду ендпоінтів.
* **Збирання Docker-образу (job `docker`):** У кожному Push та Pull Request збирається Docker-образ застосунку, контейнер запускається та проходить smoke-тест (`/health`, API каталогу, головна сторінка SPA).
* **Розгортання (CD):** У `main` код потрапляє лише через PR із зеленою перевіркою `build` (захист гілки). Після злиття Render автоматично збирає образ з того самого `Dockerfile` і розгортає його (`autoDeployTrigger: commit` у `render.yaml`); трафік перемикається на нову версію лише після успішної перевірки `/health/live`. Workflow `production-deployment.yml` фіксує деплой у GitHub (середовище `production`), щойно сайт віддає новий коміт. Режим `checksPass` не використовується: Render чекав би на всі перевірки коміту, зокрема й на цей workflow, який сам чекає на деплой.

## 6. Забезпечення надійності та доступності (REL-001 - Uptime 99.0%)

Вимога **REL-001** вимагає забезпечення щомісячного показника доступності сервісу на рівні **не менше 99.0%** (сумарний простій не більше ~7.3 годин на місяць). Для досягнення цієї мети реалізовані наступні архітектурні механізми:
1. **Автоматичний перезапуск сервісів:** Контейнери бекенду та СКБД у `docker-compose.yml` налаштовані з політикою перезапуску `restart: unless-stopped`, що забезпечує відновлення працездатності при збоях процесу за лічені секунди (MTTR < 30 с).
2. **Health Check моніторинг:** Ендпоінт `GET /health` (`src/api/routers/health.py`) виконує `SELECT 1` до бази даних і повертає `200 {"status": "ok", "database": "ok"}` або `503 {"status": "degraded", "database": "unavailable"}`. Його використовують `HEALTHCHECK` Docker-образу та smoke-тест CI. Окремий liveness-ендпоінт `GET /health/live` не звертається до БД. Його опитують платформа Render і запланований workflow `keep-alive.yml` (кожні 10 хв), який водночас є простим зовнішнім uptime-монітором і не дає безкоштовному сервісу заснути.
3. **Стійкість пулу з'єднань БД:** Використання механізму `pool_pre_ping=True` в SQLAlchemy, що автоматично перевіряє життєздатність з'єднання перед відправкою запиту та прозоро відновлює його при перезапуску сервера БД.
4. **Graceful Degradation для зовнішнього API:** У разі недоступності або обмеження квоти TMDB API система не завершує роботу з помилкою, а автоматично перемикається на вже збережені в БД метадані або локальний резервний набір (`FALLBACK_MOVIES`).
5. **ACID-транзакції:** Усі операції запису оцінок (Rating) та рецензій (Review) захищені транзакціями. У разі будь-якого апаратного збою або помилки з'єднання виконується автоматичний `ROLLBACK`, що гарантує 100% захист від пошкодження або розсинхронізації рейтингів.
