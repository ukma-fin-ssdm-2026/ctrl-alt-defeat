# Стратегія тестування (Testing Strategy)

## 1. Поточний стан тестування

Для забезпечення високої надійності та відповідності бізнес-вимогам backend-частини платформи рецензій розроблено вичерпний набір автоматизованих модульних тестів за допомогою фреймворку **pytest**.

Наразі реалізовано **237 автоматизованих тестів бекенду** у 16 тестових модулях та **87 компонентних і модульних тестів фронтенду** (Vitest), організованих за принципом Arrange-Act-Assert (AAA):
1. **`tests/test_reviews.py` (52 тести):** Повний CRUD, параметризація меж оцінок 1–10 та довжини тексту 10–5000, пагінація, фільтрація, видалення адміном (T-017) та BOLA-захист від видалення звичайним юзером (T-018), 404 (T-019), видалення через query-параметр `review_id` (SonarCloud CSRF).
2. **`tests/test_reviews_watched.py` (17 тестів):** Перевірка переглянутого перед відгуком (FR-003, FR-004, T-006, T-035), взяття автора з JWT-токена, повернення нікнейму автора та назви контенту в моделі відповіді.
3. **`tests/test_auth.py` (18 тестів):** Реєстрація, верифікація email, вхід, JWT, cookies, bcrypt-хешування (FR-001, US-011, SEC-001, T-037).
4. **`tests/test_watchlist.py` (16 тестів):** Додавання до Watchlist (T-001), захист від дублікатів 409 (T-002), видалення (T-003), збереження між сесіями (T-004).
5. **`tests/test_watched.py` (10 тестів):** Позначення контенту як переглянутого (T-011), зняття позначки через path та query-параметр (T-012), ізоляція між користувачами (T-013).
6. **`tests/test_movies.py` (14 тестів):** Пошук за назвою, фільтрація за жанром, категорією та роком (FR-002, US-003, US-005, T-009, T-010, T-014).
7. **`tests/test_movies_sorting.py` (15 тестів):** Сортування каталогу за рейтингом, датою випуску та хронометражем (FR-010, US-009, T-026..T-028).
8. **`tests/test_recommendations_api.py` (11 тестів):** Ендпоінти персоналізованих рекомендацій, сувора автентифікація з JWT (FR-007, US-007, T-020, T-021), ізоляція рекомендацій.
9. **`tests/test_recommendations_service.py` (12 тестів):** Алгоритм рекомендацій за улюбленими жанрами та рейтингами.
10. **`tests/test_comments_api.py` (20 тестів):** Деревоподібні коментарі, ліміти вкладеності, каскадне видалення (FR-011, US-010, T-029..T-031).
11. **`tests/test_comment_validation.py` (19 тестів):** Валідація тексту коментарів, захист від XSS та ReDoS (SEC-002, T-032).
12. **`tests/test_tmdb.py` (4 тести):** Інтеграція з TMDB API, кешування та Graceful Degradation (FR-012, REL-001, T-033, T-034).
13. **`tests/test_utils.py` (16 тестів):** Модерація тексту, виявлення спаму, ненормативної лексики, регресійний тест шкали 1–10 (`test_reviews_distribution_scale_1_to_10`).
14. **`tests/test_decision_table.py` (8 тестів):** Таблиця рішень для модерації (R1–R8, T-007).
15. **`tests/test_security.py` (1 тест):** Регресійний тест Bandit B104 (локальний `API_HOST`).
16. **`tests/test_main.py` (4 тести):** Глобальні Exception Handlers, генерація специфікації OpenAPI та `lifespan`.

Усі 237 модульних та інтеграційних тестів виконуються менш ніж за 18 секунд завдяки фікстурам pytest, мокінгу сесій бази даних SQLAlchemy та тестовому клієнту FastAPI TestClient.

## 3. Багаторівневий план розвитку тестування

Для переходу від суто модульного тестування до комплексної піраміди тестування визначено чіткі плани для наступних рівнів:

### 3.1. Інтеграційні тести (Integration Testing)
- **Мета:** Перевірити спільну роботу шарів FastAPI Router ↔ SQLAlchemy ORM ↔ Справжня реляційна СУБД PostgreSQL без моків.
- **Інструменти:** `pytest`, `pytest-asyncio`, `testcontainers-postgres` (підняття тимчасового Docker-контейнера з PostgreSQL на час тестів), `httpx.AsyncClient`.
- **Тестові дані:** Синтетичні набори даних у фікстурах (створення тестової схеми таблиці `reviews`, генерація 50+ записів із різними статусами `published`/`draft`, випадковими авторами `user_id` та фільмами `content_id`).
- **Трасування до вимог:**
  - **FR-003:** Фіксація транзакцій (`db.commit()`), збереження часових міток `created_at` у форматі UTC та перевірка обмежень первинного ключа `UUID4`.
  - **FR-004:** Реальна перевірка генерації SQL-запитів діалекту PostgreSQL для операторів `LIMIT`, `OFFSET` та складених фільтрів `WHERE content_id = :cid AND rating >= :min_r`.
  - **FR-012:** Перевірка конкурентного доступу (race conditions) при одночасному оновленні однієї рецензії двома запитами.

### 3.2. Системні тести (System / End-to-End Testing)
- **Мета:** Перевірка повних наскрізних користувацьких сценаріїв роботи системи у розгорнутому середовищі.
- **Інструменти:** `httpx`, `Postman` / `Newman CLI`, Docker Compose для підняття повного стеку API + DB.
- **Тестові дані:** Повні ланцюжки взаємодії (User Stories):
  1. Клієнт публікує новий відгук через `POST /api/v1/reviews`.
  2. Запит `GET /api/v1/reviews?content_id=...` підтверджує присутність створеного відгуку.
  3. Клієнт надсилає `PATCH /api/v1/reviews/{id}` для корекції оцінки та опису.
  4. Викликається модуль аналітики `generate_review_summary()` та перевіряється перерахунок середнього балу фільму.
  5. Відгук видаляється через `DELETE /api/v1/reviews/{id}`.
  6. Наступний запит `GET /api/v1/reviews/{id}` повертає статус `404 Not Found`.
- **Трасування до вимог:**
  - **US-001:** Створення та публікація відгуку глядачем.
  - **US-002:** Перегляд списку відгуків до фільму з підтримкою пагінації.
  - **US-003:** Редагування власної рецензії користувачем.
  - **US-004:** Видалення рецензії.
  - **FR-006:** Розрахунок метрик контенту на основі відгуків.

### 3.3. Приймальні тести (Acceptance Testing / UAT)
- **Мета:** Валідація відповідності системи очікуванням бізнесу та кінцевих користувачів згідно з критеріями прийнятності.
- **Інструменти:** `behave` (Gherkin BDD сценарії) або `pytest-bdd`, `Playwright` (для e2e тестування веб-клієнта).
- **Тестові дані та сценарії:**
  - *Сценарій 1 (Валідація довжини):* Given Користувач ввів рецензію довжиною 8 символів, When запит надсилається на сервер, Then повертається статус 422 із повідомленням "String should have at least 10 characters".
  - *Сценарій 2 (Антиспам та модерація):* Given Текст відгуку містить зовнішнє рекламне посилання `http://spam.org`, When користувач намагається його опублікувати, Then система відхиляє публікацію зі статусом 400 `POLICY_VIOLATION`.
  - *Сценарій 3 (Пагінація великих обсягів):* Given У системі є 25 відгуків до фільму, When запитується перша сторінка `limit=10`, Then повертається 10 записів і `has_more=true`; When запитується третя сторінка `skip=20&limit=10`, Then повертається 5 записів і `has_more=false`.
- **Трасування до вимог:**
  - **AC-001:** Обмеження розміру рецензії (10–5000 символів) та діапазону оцінки (1–10).
  - **AC-002:** Фільтрація спаму та обсценної лексики перед збереженням у базу.
  - **AC-003:** Коректність індикації пагінації (`has_more`).

## 4. Інтеграція з CI/CD та ворота якості (Quality Gates)

CI/CD конвеєр проєкту повністю налаштований та активний у файлі [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml). Він автоматично спрацьовує на кожну подію `push` та створення `pull_request` в репозиторії.

### Етапи конвеєра:
1. **Збірка та встановлення:** Інсталяція виробничих та тестових залежностей із `requirements.txt` (`pytest`, `pytest-cov`, `FastAPI`, `SQLAlchemy`, тощо).
2. **Статичний аналіз коду:** 
   - Швидкий лінтинг та перевірка стилю коду за допомогою `ruff check .`.
   - Аналіз безпеки та пошук вразливостей за допомогою `bandit -r src/api -ll`.
3. **Виконання тестів та ворота покриття (Coverage Gate):**
   - Запуск модульних тестів за допомогою `pytest --cov=src.api --cov-report=term --cov-fail-under=80 tests/`.
   - **Жорсткий поріг покриття (Coverage Gate):** встановлено прапорець `--cov-fail-under=80`. Якщо новий код знижує загальне тестове покриття нижче 80%, білд у CI автоматично вважається **проваленим** (exit code 1), блокуючи злиття pull request.
4. **Автоматична перевірка простежуваності (RTM Traceability Gate):**
   - Виконання скрипта `python3 scripts/verify_traceability.py`.
   - Перевіряє відповідність між обов'язковими тест-кейсами з `docs/requirements/rtm.md` та мітками `# Trace: T-NNN` у коді тестів. Якщо виявлено незіставлені вимоги або невідомі ID, білд переривається з `exit 1`.
5. **Контроль розбіжностей специфікації (OpenAPI Drift Check):**
   - Автоматичний запуск скрипта перевірки синхронізації `save_openapi_spec(app)`.
   - Перевірка через `git status --porcelain docs/api/openapi-generated.yaml`. Якщо розробник змінив схеми або роути в коді, але не зберіг і не закомітив оновлену специфікацію, білд падає з помилкою `OpenAPI specification is out of sync with code!`.

## 5. Розширені методи тестування (Бонусні напрями)

### 5.1. Ворота покриття (Coverage Gate)
Впроваджено у CI крок:
```bash
pytest --cov=src.api --cov-report=term --cov-fail-under=80 tests/
```
Це гарантує, що жоден регрес у покритті не потрапить до гілки `main`. Наразі проєкт демонструє покриття **99%**, що суттєво перевищує встановлений поріг 80%.

### 5.2. Тестування на основі властивостей (Property-Based Testing)
Планується інтеграція бібліотеки `Hypothesis` для тестування генеративних інваріантів:
- **Інваріант 1 (Діапазон середнього):** Для будь-якого списку валідних відгуків розміром `N > 0`, середній рейтинг `average_rating` завжди задовольняє нерівність: $1.0 \le \text{average\_rating} \le 10.0$.
- **Інваріант 2 (Цілісність розподілу):** Сума значень усіх ключів у словнику `distribution` завжди точно дорівнює значенню `total_reviews`:
  $$\sum_{k=1}^{10} \text{distribution}[k] = \text{total\_reviews}$$
- **Інваріант 3 (Санітизація тексту):** Довільні рядки довжиною понад 5000 символів або рядки з випадковими недрукованими Unicode-символами повинні або коректно валідуватися, або повертати `422`, ніколи не спричиняючи неперехоплених `500 Internal Server Error`.

### 5.3. Мутаційне тестування (Mutation Testing)
Для перевірки якості самих тестів заплановано використання інструменту `mutmut`:
- Мутаційний аналіз вносить мікрозміни в код (`>` замість `>=`, заміна констант, видалення рядків).
- Тестовий набір вважається якісним, якщо він «вбиває» понад 85% штучно створених мутантів (Mutation Score > 85%).
- Це дозволяє усунути псевдопокриття (тести, які проходять через рядки коду, але не мають суворих асертів).
