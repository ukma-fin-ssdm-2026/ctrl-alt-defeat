# Стратегія тестування

## 1. Поточний стан тестування

Для автоматизованого тестування backend-частини проєкту використовується **pytest**. Наразі реалізовано **17 автоматизованих тестів**, усі з яких успішно проходять.

Основні напрямки поточного тестування:
- **Review API:** Перевіряються CRUD-операції створення (`POST`), читання (`GET`), часткового оновлення (`PATCH`) та видалення (`DELETE`) рецензій.
- **Фільтрація та пагінація:** Перевіряється пагінація, фільтрація за `content_id` та мінімальним рейтингом `min_rating`.
- **Валідація:** Перевіряються граничні та некоректні значення рейтингу, зокрема відповіді `422 Validation Error`.
- **Обробка помилок:** Перевіряються сценарії, коли рецензію не знайдено (`404 Not Found`).
- **Допоміжна логіка:** Додано тести для `generate_review_summary`, які перевіряють кількість рецензій, середній рейтинг та розподіл оцінок.
- **Безпека:** Реалізовано regression-тести для перевірки безпеки.
- **База даних:** У тестах взаємодія з БД ізольована за допомогою mock-об'єктів.

## 2. Покриття тестами

Поточне загальне покриття коду становить **94%** — покрито 175 із 187 інструкцій.

Покриття основних компонентів:
- **База даних та ORM-моделі:** 100%.
- **Pydantic-схеми:** 100%.
- **Допоміжні функції (`utils.py`):** 100%.
- **Review API router:** 98%.
- **`main.py`:** 76%.

Непокритими залишаються переважно частини `main.py`, пов'язані з генерацією OpenAPI-специфікації, життєвим циклом та запуском застосунку. Один рядок також залишається непокритим у Review router. Основна бізнес-логіка проєкту покрита тестами.

## 3. Подальший розвиток тестування

У міру розвитку проєкту планується розширювати тестування на декількох рівнях:

- **Інтеграційні тести:** Перевірка взаємодії FastAPI, SQLAlchemy та реальної тестової бази PostgreSQL.
- **Системні тести:** Перевірка повних сценаріїв роботи API, наприклад створення → отримання → оновлення → видалення рецензії.
- **Приймальні тести:** Перевірка основних користувацьких сценаріїв відповідно до вимог системи.
- **Тестування продуктивності:** Перевірка часу відповіді API та поведінки системи при одночасних запитах.
- **Тестування безпеки:** Розширення перевірок валідації, автентифікації та авторизації, а також використання статичного аналізу безпеки.
- **Property-based тестування:** У майбутньому можливе використання Hypothesis для автоматичної генерації різних вхідних даних та перевірки граничних випадків.

## 4. Інтеграція з CI/CD

Автоматизовані тести планується інтегрувати в CI/CD-конвеєр та запускати при створенні pull request і внесенні змін до основної гілки.

CI/CD має виконувати:
- встановлення залежностей проєкту;
- запуск тестів через `pytest`;
- формування звіту про покриття;
- запуск статичних перевірок та перевірок безпеки.

Якщо обов'язкові тести не проходять, зміни не повинні потрапляти до основної гілки до виправлення проблем. Поточний рівень покриття **94%** використовується як базовий орієнтир, який необхідно підтримувати під час подальшого розвитку проєкту.
