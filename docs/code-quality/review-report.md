### Документація коду:

## 3. Пропозиції покращення

1. **Виділення сервісного шару (Service Layer):**
   - **Локація:** `src/routers/bookings.py:45-120` (хендлери `create_booking` та `update_booking`).
   - **Проблема:** Бізнес-логіка валідації статусів, перевірки часових перетинів та роботи з мок-даними розміщена безпосередньо у функціях-обробниках роутера.
   - **Рішення:** Винести цю логіку в окремий сервісний шар (`src/services/booking_service.py`), залишивши в роутерах лише приймання HTTP-запитів і делегування виконання.

2. **Уніфікація типів ідентифікаторів у схемах:**
   - **Локація:** `src/schemas/bookings.py:15` (`BookingOut.id: UUID`) vs `src/schemas/slots.py:12` (`SlotOut.id: str`), `src/mocks.py:10-25`.
   - **Проблема:** Неконсистентність типізації: частина ідентифікаторів оголошена як `UUID`, тоді як інші — як звичайні рядки `str`.
   - **Рішення:** Стандартизувати всі ідентифікатори на використанні типу `UUID4` для забезпечення суворої валідації.

3. **Уніфікація роботи з датами та часовими поясами:**
   - **Локація:** `src/schemas/bookings.py:35` (`datetime.utcnow()`) vs `src/routers/slots.py:50` (timezone-aware об'єкти з зоною `KYIV`).
   - **Проблема:** Використання застарілого `datetime.utcnow()` генерує naive datetime без часового поясу, що викликає винятки при порівнянні з timezone-aware об'єктами.
   - **Рішення:** Використовувати `datetime.now(timezone.utc)` скрізь по коду для гарантування єдиного часового стандарту UTC.

## 4. Потенційна вразливість безпеки

**Broken Object Level Authorization (BOLA / IDOR) у `patch_slot()`**
- **Локація вразливості:** `src/routers/slots.py:65-72` (функція `patch_slot`).
- **Опис проблеми:** У хендлері перевіряється лише роль користувача (`require_role(Role.PROVIDER)`), але **відсутня перевірка належності слота/приміщення** цьому провайдеру.
- **Ризик:** Зловмисник із роллю `PROVIDER` може змінити доступність або статус слота іншого постачальника послуг, знаючи або перебравши `slot_id`.
- **Рішення:** Отримати інформацію про кімнату слота та додати перевірку: `if room["provider_id"] != current_user.id: raise HTTPException(status_code=403, detail="Forbidden")`.
- **Результат:** Команда reserve-flow визнала проблему та виправила вразливість відповідно до наших рекомендацій.

### Потенційні проблеми та вразливості

#### 1. Авторизація на рівні об'єкта (IDOR/BOLA) - КРИТИЧНО
У `bookings.py` -> `update_booking`:
Хоча є перевірка ролі (`_ALLOWED_ROLE_FOR_STATUS`), перевірка `_can_view(current_user, booking)` для постачальника `Role.PROVIDER` покладається на те, чи є він постачальником кімнати. Але що, якщо статус змінюється на такий, що доступний лише іншому постачальнику?
Більш очевидна проблема в `slots.py` -> `patch_slot`:

@router.patch("/{slot_id}")
async def patch_slot(
    payload: SlotPatchIn,
    current_user: Annotated[UserOut, Depends(require_role(Role.PROVIDER))],
    slot_id: str = Path(...),
)
Тут перевіряється, що користувач є `PROVIDER`. Але **не перевіряється**, чи належить кімната цього слота саме `current_user.id`! Будь-який провайдер може закрити/відкрити слот іншого провайдера.

#### 2. Проблеми з часовими зонами
У `slots.py` -> `search_slots`:
Слоти порівнюються з `KYIV` time, але `datetime.utcnow()` використовується в `schemas/bookings.py` для `created_at`. Змішування naive (utcnow) та timezone-aware (KYIV) datetime об'єктів може призвести до складних багів при порівнянні. Краще використовувати `datetime.now(timezone.utc)` скрізь.

#### 3. Можливий витік даних (Information Disclosure)
У `auth.py` -> `issue_token`:

    if result is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Невірний email або пароль",

Це гарна практика (не казати, чи email існує). Але у `errors.py` -> `_unhandled_error_handler` стек-трейс не віддається клієнту (що добре), проте в `_http_exception_handler` деталі можуть витікати, якщо `exc.detail` містить чутливу інформацію.

#### 4. Неконсистентність ідентифікаторів
