# Code Review Report

**Команда-рецензент:** ctrl-alt-defeat  
**Проєкт на огляді:** reserve-flow (https://github.com/ukma-fin-ssdm-2026/reserve-flow)

## 3 сильні сторони

1. Код має зрозумілу модульну структуру. Роутери, схеми,
   автентифікація, обробка помилок і конфігурація розділені
   між окремими модулями, що покращує читабельність і підтримуваність.

2. Добре реалізована валідація вхідних даних за допомогою Pydantic.
   Використовуються Enum, UUID, EmailStr, обмеження Field та
   model_validator для перевірки бізнес-правил.

3. API добре документований та використовує можливості FastAPI:
   type hints, docstrings, Depends, response_model, summary,
   description та централізований формат помилок із correlation ID.

## 3 пропозиції покращення

1. Частину бізнес-логіки з роутерів варто винести в окремий
   service layer. Це спростить тестування та підтримку при
   подальшому збільшенні проєкту.

2. Варто уніфікувати типи ідентифікаторів. Наприклад,
   BookingOut використовує UUID, тоді як RoomOut та SlotOut
   використовують str для полів, які також є UUID.

3. Варто уніфікувати роботу з датою і часовими зонами.
   BookingOut використовує datetime.utcnow(), який створює
   datetime без timezone, а інші частини застосунку працюють
   з timezone-aware datetime.

## Потенційна вразливість / ризик

**Broken Object Level Authorization (BOLA / IDOR) у `patch_slot()`**
- **Опис проблеми:** У функції `patch_slot()` перевіряється наявність ролі `PROVIDER`, але **не перевіряється**, чи належить приміщення відповідного слота саме цьому постачальнику. 
- **Ризик:** Будь-який користувач із роллю `PROVIDER` потенційно може змінити доступність слота абсолютно іншого постачальника, якщо знає або перебере його ID.
- **Рішення:** Після отримання слота необхідно знайти відповідну кімнату та обов'язково додати перевірку авторизації на рівні об'єкта: `if room["provider_id"] != current_user.id: raise HTTPException(...)`.
