# Атрибути якості API

Кожна ціль нижче має три частини: число, спосіб його виміряти і умову, за якої ціль вважається невиконаною.

## Продуктивність

### Ціль 1: Час відповіді
- **Ціль:** 95-й перцентиль часу відповіді < 500 мс за умови одночасного навантаження у 100 активних користувачів.
- **Умова провалу:** p95 ≥ 500 мс під час 5-хвилинного прогону навантажувального тесту.
- **Реалізація:** Використання асинхронного фреймворку FastAPI для неблокуючої обробки запитів.
- **Вимірювання:** Навантажувальний тест інструментами k6 або JMeter.

### Ціль 2: Оптимізація обсягу даних
- **Ціль:** Розмір тіла відповіді для `GET /api/v1/reviews` ніколи не перевищує 500 КБ.
- **Умова провалу:** Хоча б одна відповідь перевищує ліміт у 500 КБ під час тестування списків.
- **Реалізація:** Сувора offset-based пагінація, де параметр `limit` жорстко обмежений діапазоном від 1 до 100 записів.
- **Вимірювання:** Моніторинг розміру payload (Content-Length) в інструментах тестування API.

## Безпека

### Ціль 1: Відсутність критичних вразливостей
- **Ціль:** Жодної знахідки рівня High у скануванні OWASP ZAP; невалідний вхід отримує статуси 400 або 422.
- **Умова провалу:** Хоча б одна знахідка рівня High або будь-яка відповідь 5xx (падіння сервера) на невалідні вхідні дані.
- **Реалізація:** Зберігання паролів виключно у захешованому вигляді (алгоритм bcrypt) та обмеження довжини тексту рецензій від 10 до 5000 символів.
- **Вимірювання:** Автоматизоване DAST-сканування (OWASP ZAP) у тестовому середовищі.

### Ціль 2: Строга типізація ресурсів
- **Ціль:** 100% параметрів шляху та тіла запиту, що ідентифікують ресурси (`review_id`, `user_id`, `content_id`), успішно відхиляють не-UUID значення.
- **Умова провалу:** Система приймає рядок, що не відповідає формату UUID4, або повертає помилку 500 замість 422 під час парсингу.
- **Реалізація:** Використання суворого типу `UUID4` у схемах валідації Pydantic на всіх відповідних ендпоінтах.
- **Вимірювання:** Автоматизовані тести з фаззингом (передача некоректних типів даних у параметри).

## Надійність

### Ціль 1: Висока доступність (Uptime)
- **Ціль:** Доступність системи (Uptime) ≥ 99.0% протягом календарного місяця.
- **Умова провалу:** Понад ~7.3 години (438 хвилин) сумарного простою протягом одного місяця.
- **Реалізація:** Використання надійної реляційної СКБД (PostgreSQL) та безперебійний деплой.
- **Вимірювання:** Зовнішній моніторинг (наприклад, UptimeRobot), що безперервно опитує сервіс.

### Ціль 2: Контрольована обробка винятків
- **Ціль:** Частка необроблених серверних помилок (HTTP 5xx) становить < 0.1% від загальної кількості запитів.
- **Умова провалу:** Кількість відповідей зі статусом 5xx перевищує 0.1% за добу.
- **Реалізація:** Глобальний обробник помилок, який формує стандартизовану модель ErrorResponse із зазначенням request_id.
- **Вимірювання:** Аналіз серверних логів та метрик (наприклад, через Prometheus / Grafana).

## Підтримуваність

### Ціль 1: Тестове покриття
- **Ціль:** Покриття вихідного коду бекенду модульними тестами (Test Coverage) ≥ 80%.
- **Умова провалу:** Звіт інструменту покриття показує результат < 80%.
- **Реалізація:** Перевірка покриття коду автоматично виконується на етапі CI/CD-пайплайну.
- **Вимірювання:** Звіт інструменту покриття коду (наприклад, `pytest-cov`).

### Ціль 2: Синхронізація документації
- **Ціль:** 100% ендпоінтів та схем у документації генеруються автоматично з коду (Code-First підхід).
- **Умова провалу:** Знайдено розбіжність між реальною поведінкою API та згенерованим файлом `openapi-generated.yaml`.
- **Реалізація:** Автоматична генерація специфікації OpenAPI під час ініціалізації (`lifespan`) FastAPI-застосунку.
- **Вимірювання:** Валідація схеми OpenAPI за допомогою автоматизованих скриптів (pre-commit hooks).
