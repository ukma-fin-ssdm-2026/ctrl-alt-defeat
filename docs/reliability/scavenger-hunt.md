### Знахідка 1 (Категорія A: Обробка помилок / Категорія D: Мовчазні збої)
**Мовчазне придушення винятків розбору токена з небезпечним fallback на неперевірене тіло запиту**

- **Файл та рядки:** [`src/api/routers/comments.py`](../../src/api/routers/comments.py#L101-L111)
- **Фрагмент коду:**
  ```python
  depth = 0
  if token:
      try:
          payload = decode_access_token(token)
          sub = payload.get("sub")
          if sub:
              user_id = uuid.UUID(sub)
              auth_user = db.query(models.User).filter(models.User.user_id == user_id).first()
              if auth_user:
                  author_name = auth_user.nickname
      except Exception:
          pass

  if user_id is None:
      raise HTTPException(
          status_code=status.HTTP_401_UNAUTHORIZED,
          detail={"code": "AUTH_REQUIRED", "message": "Please log in to leave a comment"},
      )
  ```
- **Чому небезпечна:** 
  1. Використано широкий та неспецифічний перехоплювач `except Exception: pass`, який глушить будь-які винятки (недійсний або прострочений JWT-токен, збій підключення до БД у `db.query`, помилка парсингу UUID тощо) без жодного логування (`logger.warning`/`logger.error`).
  2. До блоку `try` змінна `user_id` ініціалізується значенням `comment.user_id`, отриманим із неперевіреного тіла клієнтського запиту (`comment: CommentCreate`). Якщо клієнт передав невалідний або прострочений токен, виняток «ковтається», і обробник продовжує роботу з чужим `user_id` із тіла запиту.
  3. **Токен узагалі не потрібен:** якщо заголовка `Authorization` і cookie немає, блок `if token:` не виконується, а `user_id` лишається тим, що прийшов у тілі запиту. Перевірка `if user_id is None` пропускає такий запит.
- **Перевірка:** `POST /api/v1/comments` без токена з `{"review_id": "…", "user_id": "<id іншого користувача>", "author_name": "victim", "text": "…"}` повертає `201 Created`, коментар збережено від імені `victim`; з токеном `Bearer garbage` — так само `201`.
- **Потенційний вплив:** Будь-хто, навіть без облікового запису, публікує коментарі від імені будь-якого користувача (account impersonation) і обходить бан (FR-009), бо перевіряється бан саме підставленого користувача; у логах немає жодного сліду.

### Знахідка 2 (Категорія A: Обробка помилок)
**Необроблений виняток `IntegrityError` (Race Condition) при додаванні до списку перегляду (Watchlist)**

- **Файл та рядки:** [`src/api/routers/watchlist.py`](../../src/api/routers/watchlist.py#L65-L78)
- **Фрагмент коду:**
  ```python
  exists = (
      db.query(WatchlistItem)
      .filter(WatchlistItem.user_id == user.user_id, WatchlistItem.content_id == payload.content_id)
      .first()
  )
  if exists is not None:
      raise HTTPException(
          status_code=status.HTTP_409_CONFLICT,
          detail={"code": "ALREADY_IN_WATCHLIST", "message": "This title is already in your watchlist"},
      )

  db.add(WatchlistItem(user_id=user.user_id, content_id=payload.content_id, added_at=datetime.now(UTC)))
  db.commit()
  return content
  ```
- **Чому небезпечна:**
  Між перевіркою існування запису (`exists = ...first()`) та фактичною фіксацією в БД (`db.commit()`) існує стан гонитви (Time-of-Check to Time-of-Use — TOCTOU). При одночасному надсиланні двох однакових запитів (наприклад, подвійний клік користувача в UI або мережевий повтор) обидва запити пройдуть перевірку `exists is None`. Другий виклик `db.commit()` порушить унікальний індекс БД `(user_id, content_id)`. На відміну від [`reviews.py`](../../src/api/routers/reviews.py#L134-L141), де виняток `IntegrityError` перехоплюється з відкатом `db.rollback()`, у `watchlist.py` блок `try...except` відсутній.
- **Потенційний вплив:**
  Необроблений внутрішній збій викликає необроблену помилку `500 Internal Server Error` замість штатної `409 Conflict`, а сесія бази даних залишається у невалідному (dirty/aborted) стані.

### Знахідка 3 (Категорія A: Обробка помилок)
**Відсутність глобального обробника непередбачених винятків (`Exception`) у FastAPI**

- **Файл та рядки:** [`src/api/main.py`](../../src/api/main.py#L99-L143)
- **Фрагмент коду:**
  ```python
  # GLOBAL EXCEPTION HANDLERS

  @app.exception_handler(RequestValidationError)
  async def validation_exception_handler(request: Request, exc: RequestValidationError):
      ...

  @app.exception_handler(StarletteHTTPException)
  async def custom_http_exception_handler(request: Request, exc: StarletteHTTPException):
      ...
  ```
- **Чому небезпечна:**
  У системі визначено обробники лише для клієнтської валідації (`RequestValidationError`) та явних HTTP-винятків (`StarletteHTTPException`). Обробника винятків вищого рівня `@app.exception_handler(Exception)` немає. Будь-яка непередбачена внутрішня помилка (помилка підключення до PostgreSQL, `OperationalError`, `KeyError`, `AttributeError`) перехоплюється стандартним обробником Starlette.
- **Потенційний вплив:**
  Порушення стандартизованого формату відповіді `ErrorResponse` (клієнт отримує нестандартизований сирий текст або HTML `Internal Server Error`), відсутність збереження контексту помилки (`request_id`) у відповіді для трейсингу, а в режимі налагодження — ризик витоку внутрішніх стек-трейсів клієнту.

### Знахідка 4 (Категорія B: Зовнішні залежності та I/O)
**Блокувальний запис специфікації OpenAPI під час старту застосунку без fallback та обробки збоїв файлової системи**

- **Файл та рядки:** [`src/api/main.py`](../../src/api/main.py#L31-L44) та [`src/api/main.py`](../../src/api/main.py#L58)
- **Фрагмент коду:**
  ```python
  def save_openapi_spec(app: FastAPI):
      """Save auto-generated OpenAPI spec to file"""
      openapi_schema = app.openapi()

      os.makedirs("docs/api", exist_ok=True)
      openapi_path = Path(__file__).resolve().parents[2] / "docs" / "api" / "openapi-generated.yaml"

      with open(openapi_path, "w", encoding="utf-8") as f:
          yaml.dump(openapi_schema, f, sort_keys=False, allow_unicode=True)

  @asynccontextmanager
  async def lifespan(app: FastAPI):
      ...
      save_openapi_spec(app)
      yield
  ```
- **Чому небезпечна:**
  Функція `save_openapi_spec` викликається безпосередньо в синхронній частині життєвого циклу `lifespan` під час ініціалізації сервера. Файлова операція `open(..., "w")` не загорнута в `try...except (OSError, PermissionError)` і не має резервного сценарію. У продакшн-середовищах з контейнерами лише для читання (read-only filesystem для безпеки), або за відсутності прав на запис до каталогу репозиторію, операція викине `PermissionError`/`ReadOnlyFileSystemError`.
- **Потенційний вплив:**
  Повний крах процесу під час старту (сервіс не може запуститися і відмовити користувачеві штатно через відмову другорядної операції генерації документації).
- **Уточнення після рев'ю:** у нашому `Dockerfile` каталог `docs/api` уже належить користувачу `app`, тож на Render запис працює. Ризик реальний для інших середовищ (read-only контейнер, запуск з іншим користувачем), тому критичність знижено до середньої.

### Знахідка 5 (Категорія C: Валідація вхідних даних)
**Відсутність обмеження довжини пошукового рядка та відсутність меж для року випуску в каталозі**

- **Файл та рядки:** [`src/api/routers/movies.py`](../../src/api/routers/movies.py#L40-L54) та [`src/api/routers/movies.py`](../../src/api/routers/movies.py#L58-L65)
- **Фрагмент коду:**
  ```python
  @router.get("", response_model=PaginatedContentResponse, ...)
  def get_movies(
      search: Optional[str] = Query(None, description="Search term in title (Ukrainian or English)"),
      ...
      year: Optional[int] = Query(None, description="Release year filter (e.g., 2024)"),
      ...
  ):
      query = db.query(Content)

      if search:
          search_filter = f"%{search.strip()}%"
          query = query.filter(
              or_(
                  Content.title.ilike(search_filter),
                  Content.title_en.ilike(search_filter),
              )
          )

      if year is not None:
          query = query.filter(Content.year == year)
  ```
- **Чому небезпечна:**
  1. Параметр `search` не має обмеження `max_length`. Передача клієнтом величезного рядка (наприклад, 100 КБ або 1 МБ) формує неоптимальний шаблон `ILIKE %...%`, що спричиняє квадратичну складність пошуку за патерном у СУБД та блокує процесорні ресурси БД. Символи підстановки `%` та `_` також не екрануються.
  2. Параметр `year` не має валідації діапазону (`ge=1888, le=2100`). Клієнт може надіслати `year=-999999` або `year=2147483647`, що передається напряму в SQL-запит без швидкої відмови на рівні валідації схеми FastAPI.
- **Перевірка:** `GET /api/v1/movies?year=99999999999999999999` повертає `500 Internal Server Error`: число не вміщується в колонку `INTEGER`, і помилка драйвера БД не перехоплюється.
- **Потенційний вплив:**
  Деградація продуктивності СУБД через надважкі неіндексовані пошукові запити (ризик DoS), нераціональне навантаження на пул з'єднань БД; `500` замість `422` на некоректний рік.

### Знахідка 6 (Категорія D: Мовчазні збої / Категорія C: Валідація вхідних даних)
**Небезпечне обчислення зведення відгуків (`generate_review_summary`) із падінням при `rating: None`**

- **Файл та рядки:** [`src/api/utils.py`](../../src/api/utils.py#L5-L22)
- **Фрагмент коду:**
  ```python
  def generate_review_summary(reviews: List[Dict[str, Any]]) -> Dict[str, Any]:
      summary = {"total_reviews": 0, "average_rating": 0.0, "distribution": {i: 0 for i in range(1, 11)}}

      if not reviews:
          return summary

      total_score = 0
      for review in reviews:
          rating = review.get("rating", 0)
          total_score += rating
          if 1 <= rating <= 10:
              summary["distribution"][rating] += 1

      summary["total_reviews"] = len(reviews)
      summary["average_rating"] = round(total_score / summary["total_reviews"], 2)

      return summary
  ```
- **Чому небезпечна:**
  Конструкція `rating = review.get("rating", 0)` повертає дефолтне значення `0` лише тоді, коли ключ `"rating"` відсутній у словнику. Якщо ж ключ присутній, але його значення дорівнює `None` (наприклад, `{"rating": None}`), вираз повертає `None`. Наступний рядок `total_score += rating` викликає виняток `TypeError: unsupported operand type(s) for +=: 'int' and 'NoneType'`. Також немає захисту від нечислових типів (наприклад, рядка `"8"` або пошкоджених даних).
- **Потенційний вплив:**
  Падіння публічного ендпоінту `/api/v1/reviews/summary` із помилкою 500 для всіх користувачів фільму, якщо серед сотень рецензій хоча б одна містить `None` у полі оцінки.
- **Уточнення після рев'ю:** колонка `reviews.rating` має `NOT NULL`, а API перевіряє оцінку 1–10, тож через API така рецензія не з'явиться. Це прихована несправність (дані, змінені поза API, міграція), тому критичність низька.

### Знахідка 7 (Категорія D: Мовчазні збої / Категорія A: Обробка помилок)
**Придушення винятків без логування при верифікації пароля користувача**

- **Файл та рядки:** [`src/api/services/auth.py`](../../src/api/services/auth.py#L30-L38)
- **Фрагмент коду:**
  ```python
  def verify_password(plain_password: str, hashed_password: str) -> bool:
      """
      Verify a plain password against the stored bcrypt hash (SEC-001).
      """
      try:
          return bcrypt.checkpw(plain_password.encode("utf-8"), hashed_password.encode("utf-8"))
      except Exception:
          return False
  ```
- **Чому небезпечна:**
  Функція використовує широкий блок `except Exception: return False` без жодного виклику логера. Будь-який непередбачений виняток (наприклад, пошкоджений або некоректний формат хешу в БД, `ValueError`, помилка кодування чи баг бібліотеки bcrypt) інтерпретується просто як «невірний пароль».
- **Потенційний вплив:**
  Мовчазне маскування дефектів цілісності даних; неможливість діагностувати системну проблему розробникам/адміністраторам, оскільки в журналі подій відсутній слід системної несправності.
- **Уточнення після виправлення:** на обрізаному хеші (`$2b$12$short`) ядро `bcrypt` на Rust кидає `PanicException`, що успадковується від `BaseException`, тож `except Exception` його не ловить, і логін відповідає `500`. Критичність підвищено до середньої; виправлення та тести — у [`reliability-report.md`](reliability-report.md).

### Знахідка 8 (Категорія E: Продуктивність і блокування)
**Проблема N+1 SQL-запитів при отриманні списку переглянутого контенту (`get_watched_list`)**

- **Файл та рядки:** [`src/api/routers/watched.py`](../../src/api/routers/watched.py#L30-L45) та [`src/api/routers/watched.py`](../../src/api/routers/watched.py#L61-L69)
- **Фрагмент коду:**
  ```python
  def _build_watched_response(watched: models.WatchedItem, db: Session) -> WatchedItemResponse:
      content = db.query(models.Content).filter(models.Content.content_id == watched.content_id).first()
      return WatchedItemResponse(
          id=watched.id,
          user_id=watched.user_id,
          content_id=watched.content_id,
          created_at=watched.created_at,
          title=content.title if content else None,
          ...
      )

  @router.get("", response_model=WatchedListResponse, ...)
  def get_watched_list(
      db: Session = Depends(get_db),
      current_user: models.User = Depends(get_current_active_user),
  ):
      watched_items = (
          db.query(models.WatchedItem)
          .filter(models.WatchedItem.user_id == current_user.user_id)
          .order_by(models.WatchedItem.created_at.desc())
          .all()
      )

      items = [_build_watched_response(item, db) for item in watched_items]
      return WatchedListResponse(items=items, total=len(items))
  ```
- **Чому небезпечна:**
  Для вибірки даних про фільми використовується окремий запит у функції `_build_watched_response` всередині спискового включення. Якщо користувач має 100 переглянутих фільмів, один виклик ендпоінту виконує 101 послідовний синхронний запит до СУБД (1 запит на список id + 100 запитів на кожен `Content`) замість одного запиту з `JOIN` (як це реалізовано у `watchlist.py`).
- **Потенційний вплив:**
  Блокування робочих потоків Uvicorn на довгий час, вичерпання пулу підключень бази даних та значна затримка відповіді для активних користувачів.

### Знахідка 9 (Категорія C: Валідація вхідних даних)
**Числовий ідентифікатор фільму без меж: `500` замість `404`**

- **Файл та рядки:** [`src/api/routers/movies.py`](../../src/api/routers/movies.py) (`get_movie_by_id`)
- **Фрагмент коду:**
  ```python
  if not content and movie_id.isdigit():
      content = db.query(Content).filter(Content.id == int(movie_id)).first()
  ```
- **Чому небезпечна:** `isdigit()` пропускає рядок будь-якої довжини, а `int(...)` у Python не має меж. Число, більше за `INTEGER` у БД, драйвер не може передати в запит (`OverflowError` у SQLite, `DataError` у PostgreSQL), і виняток ніде не перехоплюється.
- **Перевірка:** `GET /api/v1/movies/99999999999999999999999` повертає `500 Internal Server Error`.
- **Потенційний вплив:** Будь-хто отримує 500 на публічному ендпоінті одним запитом; у логах — стек-трейс замість звичайного «не знайдено».

### Знахідка 10 (Категорія B: Зовнішні залежності)
**Підключення до БД без тайм-аутів з'єднання та запиту**

- **Файл та рядки:** [`src/api/db/database.py`](../../src/api/db/database.py)
- **Фрагмент коду:**
  ```python
  connect_args = {"check_same_thread": False} if DATABASE_URL.startswith("sqlite") else {}
  engine = create_engine(DATABASE_URL, connect_args=connect_args, pool_pre_ping=True)
  ```
- **Чому небезпечна:** Для PostgreSQL (Neon) не задано ні `connect_timeout`, ні `statement_timeout`, ні `pool_timeout` під наш сценарій. Безкоштовна база Neon «засинає» і прокидається кілька секунд, а при мережевому збої з'єднання може висіти довго; кожен такий запит тримає потік Uvicorn і з'єднання з пулу.

### Знахідка 11 (Категорія B: Зовнішні залежності)
**Старт застосунку не переживає недоступну БД**

- **Файл та рядки:** [`src/api/main.py`](../../src/api/main.py) (`lifespan`)
- **Фрагмент коду:**

      try:

          ...
  ```
- **Чому небезпечна:** `create_all` і сідинг звертаються до БД ще до того, як сервіс почне відповідати. Якщо Neon недоступний у момент деплою чи перезапуску, `OperationalError` обриває `lifespan` без повтору та без зрозумілого повідомлення.
- **Потенційний вплив:** Сервіс не стартує, Render перезапускає його по колу; навіть `/health/live`, якому БД не потрібна, недоступний, тож сайт повністю лежить, доки БД не повернеться.

### Знахідка 12 (Категорія A: Обробка помилок)
**Та сама гонитва, що в знахідці 2: реєстрація та список «Переглянуте»**

- **Файл та рядки:** [`src/api/routers/auth.py`](../../src/api/routers/auth.py) (`register`), [`src/api/routers/watched.py`](../../src/api/routers/watched.py) (`add_to_watched`)
- **Фрагмент коду:**
  ```python
  if db.query(User).filter(User.email == email_clean).first():
      raise HTTPException(status_code=status.HTTP_409_CONFLICT, ...)
  ...
  db.add(user)
  db.commit()
  ```
- **Чому небезпечна:** Перевірка «чи вже існує» і `commit()` розділені в часі (TOCTOU). Два одночасні запити (подвійний клік, повтор мережі) обидва проходять перевірку, а другий `commit()` порушує `UNIQUE` (`users.email`, `users.nickname`, `uq_watched_user_content`). `IntegrityError` не перехоплюється.
- **Потенційний вплив:** `500 Internal Server Error` замість `409 Conflict` при реєстрації або `200 OK` при повторному позначенні фільму переглянутим.

### Знахідка 13 (Категорія E: Продуктивність і блокування)
**Повний імпорт каталогу з TMDB синхронно під час старту**

- **Файл та рядки:** [`src/api/services/tmdb.py`](../../src/api/services/tmdb.py) (`seed_catalog_if_empty`), [`src/api/main.py`](../../src/api/main.py) (`lifespan`)
- **Фрагмент коду:**
  ```python
  if db.query(Content.id).first() is not None:
      return 0
  added = seed_movies_to_database(db, fetch_tmdb_movies())
  ```
- **Чому небезпечна:** На порожній БД із заданим `TMDB_API_KEY` під час старту виконується близько 300 HTTP-запитів до TMDB (списки + деталі кожного тайтлу), кожен з тайм-аутом 10 с. Поки `lifespan` не завершився, сервіс не відповідає на жоден запит.
- **Потенційний вплив:** Деплой на нову БД падає на перевірці здоров'я Render (сервіс «не встиг» стартувати), а при повільному TMDB старт затягується на хвилини.

### Знахідка 17 (Категорія A: Обробка помилок — довірені дані)
**Автор коментаря з тіла запиту навіть з валідним токеном**

  user_id = comment.user_id

Якщо токен валідний, але користувача з `sub` у БД немає (наприклад, акаунт видалено, а токен ще дійсний), `author_name` лишається тим, що надіслав клієнт. Це той самий корінь, що й у знахідці 1: сервер довіряє даним автора з тіла запиту.

## Етап 2: Класифікація «Несправність → Помилка → Відмова» (Threat Chain Classification)

Відповідно до класичної моделі надійності (Laprie / Avizienis / Rushby):
* **Несправність (Fault):** безпосередній дефект у програмному коді або конфігурації (причина).
* **Помилка (Error):** некоректний внутрішній стан системи, активований несправністю за певних умов виконання.
* **Відмова (Failure):** зовнішньо спостережуване відхилення поведінки сервісу від його специфікації (що бачить кінцевий користувач або залежна система).
* **Критичність (Severity):**
  * **Висока (High):** повна відмова сервісу, крах процесу, загроза безпеці або порушення ізоляції даних/авторства.
  * **Середня (Medium):** некоректні 500 помилки замість штатних кодів помилок, падіння окремих сторінок, суттєва деградація продуктивності.
  * **Низька (Low):** відсутність логів при помилці, потенційні крайові дефекти без негайного впливу на бізнес-функціонал.

---

### Детальна класифікація знахідок

#### Знахідка 1: Мовчазне придушення винятків розбору токена у коментарях
* **Несправність (Fault):** Наявність порожнього широкого блоку `except Exception: pass` та попередня ініціалізація `user_id = comment.user_id` даними з неперевіреного тіла HTTP-запиту.
* **Помилка (Error):** Без токена або з пошкодженим, простроченим чи підробленим токеном змінна `user_id` зберігає довільний ідентифікатор із тіла запиту замість переривання виконання з винятком 401.
* **Відмова (Failure):** Гість без облікового запису створює коментар від імені чужого користувача (`201 Created`, impersonation), а в логах відсутній будь-який запис про недійсний чи відсутній токен.
* **Критичність:** **Висока (High)**

#### Знахідка 2: Необроблений `IntegrityError` (Race Condition) у `watchlist.py`
* **Несправність (Fault):** Відсутність блоку перехоплення винятку `try...except IntegrityError` з відкатом транзакції `db.rollback()` навколо виклику `db.commit()` при збереженні `WatchlistItem`.
* **Помилка (Error):** Конкурентний запит порушує обмеження унікальності `UNIQUE (user_id, content_id)`, викидається виняток SQLAlchemy `IntegrityError`, і сесія БД залишається в перерваному стані (aborted/failed transaction).
* **Відмова (Failure):** Замість коректної відповіді `409 Conflict` користувач отримує помилку `500 Internal Server Error`, а повторні операції в тій самій сесії можуть зазнавати збоїв.
* **Критичність:** **Середня (Medium)**

#### Знахідка 3: Відсутність глобального обробника непередбачених винятків у FastAPI
* **Несправність (Fault):** Відсутність зареєстрованого обробника `@app.exception_handler(Exception)` на рівні екземпляра `FastAPI`.
* **Помилка (Error):** Будь-який необроблений виняток у роутерах або сервісах оминає механізм формування стандартизованої схеми `ErrorResponse`.
* **Відмова (Failure):** Клієнт API отримує нестандартизовану текстову відповідь `500 Internal Server Error` без `request_id`, документації та коду помилки; у debug-режимі можливий витік структури коду й стек-трейсів.
* **Критичність:** **Середня (Medium)**

#### Знахідка 4: Блокувальний запис OpenAPI специфікації під час старту без fallback
* **Несправність (Fault):** Виклик синхронного файлового запису `save_openapi_spec()` у життєвому циклі застосунку `lifespan` без обробки `OSError` / `PermissionError` та без перевірки прав запису.
* **Помилка (Error):** Під час старту сервісу в контейнері з read-only файловою системою виникає неперехоплений виняток `PermissionError`.
* **Відмова (Failure):** Сервіс не може запуститися та аварійно завершує роботу контейнера (`CrashLoopBackOff`); повна відмова в обслуговуванні для всіх користувачів.
* **Критичність:** **Середня (Medium)** — у поточному `Dockerfile` каталог доступний для запису (див. уточнення в Етапі 1).

#### Знахідка 5: Відсутність обмеження довжини пошукового рядка та меж року в каталозі
* **Несправність (Fault):** Відсутність параметрів валідації `max_length` для `search` та діапазону `ge`/`le` для `year` у визначенні `Query` ендпоінту `get_movies`.
* **Помилка (Error):** Генерація важкого SQL-запиту з гігантським патерном `ILIKE %...%` або виконання запиту з некоректними числовими межами дат.
* **Відмова (Failure):** Довге очікування відповіді клієнтом (аж до таймауту HTTP Gateway 504), різке зростання навантаження на CPU бази даних (ризик відмови в обслуговуванні).
* **Критичність:** **Середня (Medium)**

#### Знахідка 6: Небезпечне обчислення зведення відгуків (`TypeError` при `rating: None`)
* **Несправність (Fault):** Відсутність захисної перевірки (guard check) типу та наявності `None` перед виконанням складання `total_score += rating` у функції `generate_review_summary`.
* **Помилка (Error):** Спроба виконати операцію `int + NoneType`, що викидає неперехоплений виняток `TypeError`.
* **Відмова (Failure):** Помилка `500 Internal Server Error` на запит публічного рейтингу фільму `/api/v1/reviews/summary`; користувачі не бачать відгуків та рейтингу фільму.
* **Критичність:** **Низька (Low)** — через API така оцінка не потрапить у БД (див. уточнення в Етапі 1).

#### Знахідка 7: Придушення винятків без логування при верифікації пароля
* **Несправність (Fault):** Блок `except Exception: return False` у функції `verify_password` без виклику `logger.warning` або `logger.error`.
* **Помилка (Error):** Внутрішній системний збій (пошкоджений хеш у базі даних, збій кодування UTF-8, збій бібліотеки bcrypt) призводить до повернення булевого `False` замість реєстрації збою системи.
* **Відмова (Failure):** Користувач не може ввійти в обліковий запис і отримує стандартне повідомлення «Невірні облікові дані», а адміністратори та розробники не отримують жодного сигналу про системну несправність у логах.
* **Критичність:** **Низька (Low)**

#### Знахідка 8: Проблема N+1 SQL-запитів у списку переглянутого (`get_watched_list`)
* **Несправність (Fault):** Окремий виклик `db.query(models.Content)` для кожного елемента списку `watched_items` всередині генератора списку замість об'єднання таблиць через SQL `JOIN`.
* **Помилка (Error):** Виконання $N+1$ синхронних викликів до СУБД в межах одного HTTP-запиту, що блокує потік пулу підключень до бази даних.
* **Відмова (Failure):** Суттєва затримка відповіді (latency spike) під час відкриття користувачем сторінки переглянутих фільмів; ризик вичерпання пулу з'єднань БД при високому навантаженні.
* **Критичність:** **Середня (Medium)**

#### Знахідка 9: Числовий ідентифікатор фільму без меж
* **Несправність (Fault):** `movie_id.isdigit()` без обмеження довжини та `int(movie_id)` без перевірки діапазону `INTEGER`.
* **Помилка (Error):** Драйвер БД не може передати число в запит (`OverflowError` / `DataError`).
* **Відмова (Failure):** `500 Internal Server Error` на `GET /api/v1/movies/{id}` замість `404 CONTENT_NOT_FOUND`.
* **Критичність:** **Середня (Medium)**

#### Знахідка 10: БД без тайм-аутів
* **Несправність (Fault):** `create_engine` без `connect_timeout` / `statement_timeout`.
* **Помилка (Error):** Потік Uvicorn і з'єднання з пулу заблоковані в очікуванні відповіді БД.
* **Відмова (Failure):** Запити висять до тайм-ауту проксі; при вичерпанні пулу зависає весь сайт.
* **Критичність:** **Висока (High)**

#### Знахідка 11: Старт без БД
* **Несправність (Fault):** `create_all` і сідинг у `lifespan` без обробки `OperationalError` і без повтору.
* **Помилка (Error):** Виняток обриває ініціалізацію застосунку.
* **Відмова (Failure):** Сервіс не стартує й перезапускається по колу; сайт недоступний повністю.
* **Критичність:** **Висока (High)**

#### Знахідка 12: Гонитва при реєстрації та в «Переглянутому»
* **Несправність (Fault):** Перевірка існування й `commit()` без `try...except IntegrityError`.
* **Помилка (Error):** Порушення `UNIQUE`, сесія в перерваному стані.
* **Відмова (Failure):** `500` замість `409` (реєстрація) або `200` (переглянуте).
* **Критичність:** **Середня (Medium)**

#### Знахідка 13: Імпорт TMDB під час старту
* **Несправність (Fault):** Синхронний імпорт ~300 запитів у `lifespan` на порожній БД.
* **Помилка (Error):** Ініціалізація застосунку триває хвилини, сервіс не приймає запити.
* **Відмова (Failure):** Деплой падає на перевірці здоров'я Render.
* **Критичність:** **Середня (Medium)**

#### Знахідка 14: Фронтенд без тайм-ауту
* **Несправність (Fault):** `axios.create` без `timeout`.
* **Помилка (Error):** Проміс запиту не завершується, поки бекенд висить.
* **Відмова (Failure):** Нескінченне «Завантаження…» без можливості повторити дію.
* **Критичність:** **Середня (Medium)**

#### Знахідка 15: Числові змінні середовища
* **Несправність (Fault):** `int(os.getenv(...))` під час імпорту модуля без обробки помилки.
* **Помилка (Error):** `ValueError` на етапі імпорту.
* **Відмова (Failure):** Сервіс не стартує, причина в лозі неочевидна.
* **Критичність:** **Низька (Low)**

#### Знахідка 16: Стан оновлення каталогу лише в пам'яті
* **Несправність (Fault):** Стан фонового імпорту не зберігається поза процесом.
* **Помилка (Error):** Після перезапуску стан скидається на `idle`, частковий імпорт ніде не зафіксовано.
* **Відмова (Failure):** Адміністратор не бачить, що імпорт обірвався.
* **Критичність:** **Низька (Low)**

#### Знахідка 17: Автор коментаря з тіла запиту при валідному токені
* **Несправність (Fault):** Поля `user_id` і `author_name` у `CommentCreate` і їх використання як значень за замовчуванням.
* **Помилка (Error):** Ім'я автора береться від клієнта, якщо користувача з токена немає в БД.
* **Відмова (Failure):** Коментар з довільним іменем автора.
* **Критичність:** **Середня (Medium)**
