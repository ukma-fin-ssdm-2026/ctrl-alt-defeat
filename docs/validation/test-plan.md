# План тестування (Test Plan) 

**Обсяг:** Тестуємо ключові користувацькі потоки: реєстрацію/авторизацію (FR-001), систему відгуків та модерацію (FR-003, FR-004, FR-008, FR-009, SEC-002), а також перегляд списку відгуків з пагінацією та фільтрацією (US-008). 

**Свідомо НЕ тестуємо на цьому етапі:** US-001 (Watchlist), оскільки цей функціонал ще не імплементовано і він винесений у наступний спринт. Для тестів нереалізованого функціоналу (рольові перевірки BOLA, бан користувачів) у тест-плані встановлюється статус `[xfail: заплановано]`.

**Критерії виходу:** Усі наявні тести плану зелені в CI (GitHub Actions: раннер `ubuntu-latest`), покриття коду бекенду перевіряється через `pytest-cov` із встановленим жорстким порогом `--cov-fail-under=80` (фактичне покриття 99%), відсутні відкриті критичні дефекти безпеки за сканером Bandit.

**Ризики:** Найімовірніше зламається безпека при обробці користувацького тексту (XSS-ін'єкції та спам у відгуках — SEC-002) та швидкодія під час навантаження (PERF-001). Системний тест навантаження (кейс 8) автоматизовано через k6-скрипт `tests/perf/k6-search.js` та винесено в окремий прогін, щоб не сповільнювати швидкий CI.

### Тести поточного спринту (PR #108 та PR #109)

Для забезпечення повної відповідності реалізованого коду тест-плану внесено тести, розроблені в межах PR #108 та PR #109:

#### 1. CRUD-операції та параметризація меж (PR #108, `tests/test_reviews.py`):
- `test_create_review_valid_ratings_boundary` — параметризована перевірка допустимих значень рейтингу `[1, 2, 5, 9, 10]` (201 Created).
- `test_create_review_invalid_ratings_boundary` — параметризована перевірка неприпустимих значень рейтингу `[0, -1, -10, 11, 100, 999]` (422 Validation Error).
- `test_create_review_text_length_boundaries` — перевірка граничних довжин тексту: 9 (422), 10 (201), 200 (201), 5000 (201), 5001 (422).
- `test_get_reviews_min_rating_filter` — параметризована фільтрація за `min_rating` (`[1, 5, 8, 10]`) з інспектуванням виразу SQLAlchemy.
- `test_get_reviews_with_content_filter` та `test_get_reviews_with_user_filter` — фільтрація списку рецензій за контентом та автором.
- `test_get_review_by_id_success` / `test_get_review_by_id_not_found` — отримання рецензії за UUID або 404 помилка.
- `test_update_review_success` / `test_update_review_not_found` / `test_update_review_invalid_data` — часткове оновлення (PATCH).

#### 2. Специфікація та перевірка політик модерації (PR #109, `tests/test_utils.py`):
- `test_policy_clean_text` — пропуск валідного тексту без порушень.
- `test_parameterized_policy_violations` — виявлення спам-посилань (`spam_links`), обсценної лексики (`profanity`), крику (`shouting`) та обфускації (sh1t, f*ck).
- `test_policy_multiple_violations` — комбінація декількох порушень в одному тексті.
- `test_policy_false_positives` — захист від помилкових спрацьовувань (слова "classic", "shift").
- `test_policy_empty_text` — коректна обробка порожнього рядка.
- `test_create_review_policy_violation` та `test_update_review_policy_violation` — інтеграція модерації в роути `POST` та `PATCH` (повернення 400 `POLICY_VIOLATION`).

## Бонуси

### 1. Автоматична перевірка простежуваності (Automated Traceability)
Скрипт `scripts/verify_traceability.py` інтегровано в CI workflow (`.github/workflows/ci.yml`). Він зіставляє ID вимог і тест-кейсів із `docs/requirements/rtm.md` із мітками `# Trace: T-NNN` у тестовому коді.
- **Логіка перевірки:** Скрипт автоматично виявляє:
  1. Тест-кейси, які обов'язкові для реалізованих історій, але не мають відповідного тесту в коді (gaps) — спричиняє завершення з кодом помилки `exit 1`.
  2. Тести, що посилаються на неіснуючі в RTM ідентифікатори (orphans) — також валить білд.
- **Червоний прогін (дірку знайдено):** До додавання коментарів `# Trace: T-017` та `# Trace: T-038` скрипт виявив відсутність зв'язку для обов'язкових вимог і завалив перевірку з кодом 1:
  ```
  FAIL: 2 required T-ID(s) have no tests:
     T-017 (US-006)
     T-038 (US-008)
  Traceability check FAILED.
  ```
- **Зелений прогін (дірку закрито):** Після зіставлення тестів у `tests/test_reviews.py` скрипт підтвердив 100% покриття обов'язкових T-ID:
  ```
  PASS: All required T-IDs are covered by tests.
  PASS: All test traces reference valid RTM T-IDs.
  Traceability check PASSED.
  ```

### 2. Тести з техніки тест-дизайну: Таблиця рішень (Decision Table)
Для модуля модерації та перевірки політик (`check_review_policy_violations`) побудовано таблицю рішень на 3 булеві фактори ($2^3 = 8$ правил):
- **F1 (URL):** Текст містить спам-посилання `http://` або `https://`
- **F2 (Profanity):** Текст містить ненормативну або обфусковану лексику (sh1t, f*ck тощо)
- **F3 (Shouting):** Текст довжиною > 20 символів містить понад 80% великих літер (CAPS LOCK)

| ID правила | F1 (URL) | F2 (Profanity) | F3 (Shouting) | Очікуваний результат (список порушень) | Тест-кейс у коді |
|------------|----------|----------------|---------------|----------------------------------------|------------------|
| **R1** | Ні | Ні | Ні | `[]` (чистий текст) | `test_decision_table_content_moderation[R1]` |
| **R2** | Так | Ні | Ні | `["spam_links"]` | `test_decision_table_content_moderation[R2]` |
| **R3** | Ні | Так | Ні | `["profanity"]` | `test_decision_table_content_moderation[R3]` |
| **R4** | Ні | Ні | Так | `["shouting"]` | `test_decision_table_content_moderation[R4]` |
| **R5** | Так | Так | Ні | `["profanity", "spam_links"]` | `test_decision_table_content_moderation[R5]` |
| **R6** | Так | Ні | Так | `["shouting", "spam_links"]` | `test_decision_table_content_moderation[R6]` |
| **R7** | Ні | Так | Так | `["profanity", "shouting"]` | `test_decision_table_content_moderation[R7]` |
| **R8** | Так | Так | Так | `["profanity", "shouting", "spam_links"]` | `test_decision_table_content_moderation[R8]` |

Тести реалізовано як параметризований набір у `tests/test_decision_table.py::test_decision_table_content_moderation`, де кожен тестовий випадок зіставлено з відповідним ID правила (R1–R8) та прив'язано до вимоги `# Trace: T-007`.

### 3. Тести як специфікація для агента

«Використання ШІ»
Згенеровано функцію `check_review_policy_violations` для автоматичного аналізу тексту рецензій на предмет порушень (спам-посилання, нецензурна лексика, надмірне використання CAPS LOCK).
1. Спочатку було написано 7 тестів-специфікацій, які перевіряють різні види порушень. Зроблено коміт із тестами, що падали (`c076fae`). 
2. Потім специфікацію передано ШІ-агенту (Gemini), отримано реалізацію на базі Regex та зроблено коміт з робочим кодом (`0590064`).
3. Всього знадобилося 2 ітерації: спочатку отримано базовий фільтр за словником, а на другій ітерації ШІ використав регулярні вирази для розпізнавання обфускованої лексики (напр., sh1t).
