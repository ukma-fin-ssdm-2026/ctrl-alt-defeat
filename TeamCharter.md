## 4. Співпраця та робочий процес
- **Стратегія гілкування:** GitHub Flow (створення окремих гілок для нових функцій `feature/...` або виправлень `fix/...`, з подальшим Pull Request до `main`).
- **Практики комітів:** Регулярні коміти. Повідомлення комітів мають бути чіткими, описовими та відповідати формату Conventional Commits.
- **Правила огляду коду:** Всі злиття в `main` вимагають Pull Request та принаймні 1 схвалення (Approve) від іншого учасника команди.
- **Робочий процес завдань:** Відкрити Issue → Призначити на виконавця (Assignee) → Працювати в окремій гілці → Створити PR, що закриває Issue → Провести Code Review → Злити (Merge) та закрити.

**Практики роботи з вимогами**
- **Перегляд користувацьких історій (User Stories):** Написані користувацькі історії проходять обов’язкове рецензування (через механізм Pull Request Review) перед їх злиттям у гілку main. Керівник вимог перевіряє дотримання формату "Як <роль>, я хочу <дія>, щоб <ціль>" та наявність критеріїв приймання (Acceptance Criteria).
-	**Перевірка нефункціональних вимог (NFRs):** Нефункціональні вимоги перевіряються під час спільних онлайн-сесій огляду командою. Керівник якості підтверджує, що кожна NFR містить чіткі вимірювані критерії (наприклад, час відгуку < 2 сек), які можна протестувати.

## 5. Управління артефактами
- **Локація документів:** Усі документи, пов'язані з вимогами (користувацькі історії, NFR, матриця RTM), повинні зберігатися виключно в каталозі /docs/requirements/ нашого репозиторію.
- **Підтримка README.md:** Керівник документації зобов’язаний підтримувати головний файл README.md в актуальному стані, забезпечуючи наявність робочих посилань на всі створені артефакти вимог та поточний статут.

## 6. Індивідуальна відповідальність та презентація (Loom)
- **Демонстрація внеску:** Кожен учасник команди записує індивідуальну відео-презентацію в Loom. У відео учасник повинен чітко показати свій особистий внесок у роботу (наприклад, написані ним користувацькі історії, додані нефункціональні вимоги або конкретні зв'язки, задокументовані в RTM).
- **Перевірка доказів:** Докази роботи кожного учасника збираються за допомогою історії комітів (Git commit log) та історії Pull Requests. Перед записом відео команда проводить коротку звірку, щоб переконатися, що авторство (Assignees/Authors) в Issue та PR відповідає фактичній роботі.
- **Примітка для відповідального за статут:** Під час запису свого відео, відповідальний за статут демонструє історію версій (Git commit log) файлу TeamCharter.md, щоб підтвердити внесення оновлень за результатами Лабораторної роботи 2.

## 7. Вирішення конфліктів
- **План вирішення конфліктів:** 
  1. Відкрите обговорення проблеми на найближчій зустрічі команди.
  2. Прийняття рішення шляхом голосування більшістю.
  3. Якщо консенсусу не досягнуто або голоси розділилися порівну, проблема ескалюється до викладача для остаточного вирішення.

## 8. Доступність та робоче навантаження
- **Доступність учасників:** Кожен учасник очікує виділяти приблизно 8-10 годин на тиждень для роботи над проєктом.
- **Балансування навантаження:** Якщо хтось із команди перевантажений завданнями, він повинен повідомити про це в чаті. Невиконані задачі (Issues) будуть перерозподілені на найменш завантажених учасників.

## 9. Етична та професійна поведінка
- **Спільні принципи:** Усі учасники зобов'язуються дотримуватися правил академічної доброчесності НаУКМА та Кодексу етики ACM. Ми не допускаємо плагіату чужого коду чи документації. Усі члени команди ставляться одне до одного з повагою, підтримують конструктивну критику та уникають токсичної поведінки.

## 10. Використання ШІ
- **Інструменти:** Команда може використовувати GitHub Copilot, ChatGPT, Gemini та інші кодові асистенти для генерації шаблонів, рефакторингу або пояснення складних концепцій.
- **Правила розкриття:** Будь-яке суттєве використання ШІ для написання коду або документації має супроводжуватися нотаткою «Використання ШІ» в коментарях до Pull Request або в артефактах лабораторних робіт.
- **Правило верифікації:** Увесь згенерований ШІ код проходить обов'язковий перегляд (Code Review) людиною та тестування перед злиттям. Неперевірений згенерований код ніколи не потрапляє в основну гілку `main`.
