## 4. Співпраця та робочий процес
- **Стратегія гілкування:** GitHub Flow (створення окремих гілок для нових функцій `feature/...` або виправлень `fix/...`, з подальшим Pull Request до `main`).
- **Практики комітів:** Регулярні коміти. Повідомлення комітів мають бути чіткими, описовими та відповідати формату Conventional Commits.
- **Правила огляду коду:** Всі злиття в `main` вимагають Pull Request та принаймні 1 схвалення (Approve) від іншого учасника команди.
- **Робочий процес завдань:** Відкрити Issue → Призначити на виконавця (Assignee) → Працювати в окремій гілці → Створити PR, що закриває Issue → Провести Code Review → Злити (Merge) та закрити.

**Практики роботи з вимогами**
- **Перегляд користувацьких історій (User Stories):** Написані користувацькі історії проходять обов’язкове рецензування (через механізм Pull Request Review) перед їх злиттям у гілку main. Керівник вимог перевіряє дотримання формату "Як <роль>, я хочу <дія>, щоб <ціль>" та наявність критеріїв приймання (Acceptance Criteria).
-	**Перевірка нефункціональних вимог (NFRs):** Нефункціональні вимоги перевіряються під час спільних онлайн-сесій огляду командою. Керівник якості підтверджує, що кожна NFR містить чіткі вимірювані критерії (наприклад, час відгуку < 2 сек), які можна протестувати.

## 11. Політика якості та огляду коду

**Основний стандарт кодування:**
- У проєкті використовується галузевий стандарт **PEP 8** для Python.
- **Іменування:** `snake_case` для змінних та функцій (ясність понад стислість), `PascalCase` для класів, `UPPER_SNAKE_CASE` для констант.
- **Форматування:** 4 пробіли для відступів, без табуляцій. Максимальна довжина рядка — 120 символів.
- **Правило бойскаута (Boy Scout Rule):** Залишай код кращим, ніж знайшов. Якщо учасник торкається файлу, він приводить його до стандарту.

**Інструменти лінтингу та аналізу безпеки:**
- Усі перевірки автоматизовані за допомогою **pre-commit**. 
- **Лінтинг та автоформатування:** Використовується **Ruff** (або Flake8 + Black) для автоматичного вирівнювання коду та пошуку стилістичних помилок.
- **Аналізатор безпеки:** Використовується **Bandit** для статичного аналізу Python-коду на наявність поширених вразливостей (наприклад, хардкод паролів, небезпечні налаштування).

**Процес Code Review:**
1. **Створення PR:** Увесь новий код додається виключно через Pull Request у гілку `main`.
2. **Автоматичні перевірки:** Перед оглядом код повинен успішно пройти всі автоматичні перевірки CI (Ruff, Bandit (Pytest), OpenAPI генерація).
3. **Огляд колегою:** Обовʼязковий перегляд і мінімум 1 схвалення (Approve) від іншого учасника команди.
4. **Фокус перевірки:** На огляді перевіряється виключно бізнес-логіка, архітектура та безпечна обробка помилок (fail securely). Суперечки щодо форматування заборонені — це завдання лінтерів.

**Критерії готовності коду:**
1. **Форматування:** Код успішно пройшов усі локальні та CI-перевірки лінтерів (Ruff) без попереджень.
2. **Безпека:** Статичний аналіз (Bandit) не виявив вразливостей. Помилки обробляються безпечно (без витоку внутрішніх деталей системи користувачу).
3. **Тести:** Нова логіка покрита тестами, і всі тести (як старі, так і нові) проходять успішно (зелений статус у CI).
4. **Документація:** Додані обґрунтовані коментарі (які пояснюють "чому", а не "що") та docstrings для нових функцій. OpenAPI специфікація (`openapi-generated.yaml`) успішно згенерована і синхронізована з кодом.
